# 代码 ↔ 文档同步契约

> 文档驱动开发最危险的失败模式不是「没有文档」，而是**文档与代码漂移**——代码是活物、文档是快照，
> 写在 `docs/<feature>/` 里的领域模型 / 数据契约一旦没跟上实现，就会变成「谎言」，下一个接手者基于错误假设做改动。
>
> 本文件定义**「工程 → 文档」的同步契约**：哪些代码改动、必须回写哪份文档、以及交付前如何对账。
> 定位是**治理式纪律 + 交付门对账**（不做代码解析自动比对，靠硬规则 + 可机检对账产物兜底）。

---

## 1. 核心原则（先立规矩）

1. **代码是 truth，文档是契约的投影**。任一时刻，「代码实际怎么做」与「文档宣称怎么做」不一致时：
   - 若代码是**有意偏离**已确认的文档 → 必须先回到对应闸门（a/p/b/c）重新确认，不能静默改码。
   - 若代码是**实现过程中的正确结果**（比如合并了字段、补了边界）→ **必须回写文档**，让文档跟上代码。
2. **改代码 = 改文档**，两步绑定，不允许只改其一。这是实现阶段的硬纪律，不是可选动作。
3. **对账在交付门强制做**：阶段 6 交付前，必须产出「一致性对账」产物，逐项核对「文档宣称 ↔ 代码实现」，
   漂移项要么回写文档、要么回退代码，不允许「带着漂移交付」。
4. **原型也是文档**：`02-原型/<批次>/原型说明.md` 与 `原型图.html` 同样受本契约约束——实现中改了页面结构、
   屏数、交互状态或视觉 token，必须回写原型文档，不能只改代码。
5. **架构层是全局约束，别处改动必须回写它并留台账**：`03-架构/` 是**项目总体架构约束层**——全项目唯一的
   架构真相，跨批次共享、不随需求分叉。别处改动一旦触及它的任何一条内容，必须**增量更新**它（不只改代码），
   并在该档「增量更新记录」追加一行。细则见 2.1。

---

## 2. 同步点映射表（改哪些代码 → 回写哪份文档哪一节）

这是本契约的执行核心。实现阶段（阶段 5）每改一处代码，先查下表，命中即回写对应文档章节：

| 代码侧的改动 | 必须回写的文档产物 | 回写到哪个章节 | 说明 |
|---|---|---|---|
| 新增 / 删除 / 改动实体、字段、值对象、类型、默认值 | `01-需求/<批次>/领域模型.md` | 「术语表」「实体」 | 契约本体在此；字段变了术语未必变，两处都要核 |
| 领域规则 / 不变量变化（校验、边界） | `01-需求/<批次>/领域模型.md` | 「不变量」 | 不变量带编号，改条文要同步改「违反时的行为」 |
| 枚举取值语义增减 | `01-需求/<批次>/领域模型.md` | 「枚举与取值域」 | 取值**语义**在此；线格式 / 未知值处理在下面那份跨端档 |
| **双端字面 / 调用姿势 / 口径 / 错误语义变化** | **`01-需求/<批次>/跨端共享需求.md`** | **「命名规范」「共享接口规范」「共享数据契约」「枚举与取值域」「跨端一致性铁律」「失败与错误语义」** | **仅两端的项目才产出；改一端必须核另一端。这是跨端契约的事实源** |
| **页面结构 / 屏数 / 交互状态变化** | **`02-原型/<批次>/原型说明.md`** | **「页面清单」「关键交互」「状态覆盖」** | **新增一屏、合并两屏、砍掉某状态都必须回写；漂移原型是最易被忽略的一类** |
| **视觉 token / 配色 / 字号 / 间距变化** | **`02-原型/<批次>/原型说明.md`** | **「视觉稿规格」** | **改了 `原型图.html` 的 CSS 变量就要同步规格表** |
| **模块边界 / 依赖方向 / 序列化与持久化实现 / seam / 架构级约束变化** | **`03-架构/` 下受影响的档**（通常含 `跨端共享层.md`、`设计约束.md`、`方案草案.md`） | 各档对应章节 | **架构层只登记「契约落在哪、怎么实现」，不重抄契约内容**。**命中本行还须按 2.1 在架构层留增量台账** |
| 公开接口签名 / 导航 / 资源改动 | `04-落地计划/<批次>/变更清单-*.md`（最新一份） | 「签名/导航/资源变更」 | 与闸门 c1 的变更清单对齐 |
| 新增/升级第三方依赖 | `04-落地计划/<批次>/变更清单-*.md`（最新一份） | 「依赖」 | 含版本号 |
| 需求范围内外变化（补了边界案例 / 扩了范围） | `01-需求/<批次>/需求-*.md` + `01-需求/<批次>/用户故事-*.md` | 「边界」「非目标」「验收场景」 | 扩范围禁止静默，必须回闸门 a；**回写是新建下一个编号**，不改旧文件 |
| 测试计划外新增/删掉的测试 seam | `05-实现与测试/<批次>/测试计划.md` | 「seam」「should 用例」 | 保证测试计划与真实测试一致 |

> **回写粒度**：文档里的实体/字段/不变量/屏 id，应与代码中的对应声明**同名一致**（移动端允许语言级不同，
> 但语义与命名要对得上，尤其跨端时字段名必须同义）；原型屏 id 与 `原型图.html` 的 `data-screen` 必须逐字一致。

### 2.1 `03-架构/` 的双向同步：全局约束 + 增量更新（最易被漏）

`03-架构/` 不是「阶段 3 的产出物堆」，而是**项目总体架构约束层**——全项目唯一的架构真相，
跨批次共享、**不随需求分叉、不因批次新建**。因此它比任何单批次文档都更容易、也更危险地失真：
**一个批次的改动若没回写架构层，后续所有批次都会基于过期的约束做设计。**

| 方向 | 触发 | 义务 |
|---|---|---|
| **本层 → 别处** | `03-架构/` 任一档变更 | 同步 **文档 + 代码 + 所有活跃批次**的相关产物（尤其各批次的 `跨端共享需求.md` / `领域模型.md` / `原型说明.md`） |
| **别处 → 本层** | 代码 / `01-需求` / `02-原型` / `04-落地计划` / 本目录其他档 改动，且触及本层所辖内容 | **本层必须同步增量修订**：只改受影响条目、**不整篇重写**；并在该档文末「增量更新记录」**追加一行台账** |

**「增量更新」的判定**：别处的一处改动，若改变了架构层的**任何一条**已写内容（模块边界、依赖方向、契约落点、
序列化方式、seam、约束条目），即为命中。命中了却只改代码不改架构层 = 漂移。

**台账必填四要素**：日期 · 触发来源（哪份产物/哪处代码改了什么）· 本文件更新了什么 · 影响批次。

> **为什么架构层要单独立这条**：单批次文档漂移只影响该批次；**架构层漂移会同时毒化所有批次**，
> 且因为它是「全局单例」，下一个批次开工时读到的就是过期约束——错误会被继承而不是被发现。
> 所以架构层是全项目里**唯一**被要求「留增量轨迹」的一层（收敛型只说「不编号」，不排除留台账）。
>
> **机检兜底**：`03-架构/` 全部 7 份产物的「增量更新记录」章节是 `scan-artifacts.py` 的必填锚点，
> 缺了则该产物校验不过；台账内容是否真实填对由交付门 `一致性对账` 人工/模型核。

---

## 3. 交付门的一致性对账（硬步骤）

阶段 6 交付门（在 `code-review` 与产出交付报告之间）必须做一次「代码 ↔ 文档」对账，产出
`06-交付/<批次>/一致性对账-NN-<短名>.md`（照 `templates/06-交付/一致性对账-00-<短名>.md` 填空）。对账基线 = 阶段 2/3/4 已确认的契约文档（含原型）。
**每做一轮交付对账就是新建下一个编号**（追加型），历史对账记录不可变。

对账逐项走这三类，任一「未同步」项都要当场处理：

| 判定 | 含义 | 处理 |
|---|---|---|
| ✅ 已同步 | 文档与代码一致 | 记录 PASS |
| ⚠️ 漂移 | 代码变了、文档没跟上 | **回写文档**后记为已同步；若代码是错误实现则回退代码 + 回闸门 |
| ❓ 需复核 | 不确定是否漂移（如动态性强的语言） | 标出、人工确认，不默认放行 |

> **对账是本契约的「落地支点」**：不靠人自觉记得同步，而是靠交付门前这一步**把漂移暴露出来**。
> `scan-artifacts.py` 会把 `06-交付/<批次>/一致性对账-*.md` 作为阶段 6 的必填产物卡住（含「同步点」「漂移项」章节），
> 缺了就无法通过结构校验。

---

## 4. 与现有机制的关系（不重复、不冲突）

- **单向「文档 → 工程」**（现有）：闸门 a/p/b/c 保证写码前有文档；本契约补上**反向「工程 → 文档」**，形成闭环。
- **校验器分工**：`scan-artifacts.py` 只查「对账产物存在 + 章节在场」，不做代码↔文档的语义比对——
  语义对账由交付门的人工/模型步骤完成，写入对账产物。避免把「查漂移」做成不靠谱的代码解析。
- **lite 档**：对账步骤**不因档位而省略**（这是约束不是仪式），但 lite 档对账覆盖的同步点按 `config/tier.json`
  收缩后的产物集执行（即只对账仍然产出的那份文档，**原型两项仍在对账范围内**）。

---

## 5. 何时本契约会被触发

- 阶段 5（实现）每改一处代码 → 触发「同步点映射」回写（含原型文档）。
- 阶段 6（交付）交付门前 → 触发「一致性对账」产出对账产物。
- 阶段 7（反馈）回跳重跑 → 若回跳原因是「漏同步」，回到对应对账项补写。
- **回跳本身也受约束**：若实现发现流程走不通，正确做法是回退到**阶段 2 原型**重画并经闸门 p 再确认，
  而不是绕过原型硬改代码。
