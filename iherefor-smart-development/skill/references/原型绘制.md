# 原型绘制（视觉稿 + 交互原型）

> 本文件是 `iherefor-smart-development` **阶段 2 原型设计**的方法论与执行规范。
> 阶段 1（需求理清）确认后、阶段 3（架构设计）开始前执行；产物落 `docs/<feature>/02-原型/<批次>/`（`<批次>` = `NN-需求名`，与 `01-需求/<批次>/` **同名对齐**），闸门 🔒 **p（原型门）**。
>
> **本 skill 自包含**：原型绘制由本流程自己的规范 + `templates/02-原型/<批次>/原型图.html` 模板实现，**不依赖任何其它 skill**。
> （若日后确需引入外部 HTML 设计类 skill 做增强，走阶段 0 的 `install-local-skill` 流程登记；属可选增强，不是默认路径。）

---

## 1. 为什么把原型插在 Spec 与 Plan 之间

需求文档描述的是「文字上的行为」，架构文档描述的是「代码上的结构」。两者之间缺一层**看得见的共识物**——
不把「用户看到的界面、视觉观感、屏与屏怎么走」先钉死，架构就只能靠脑补，等实现完才发现屏接不上、信息层级不对。
原型就是这层桥：把 Spec 的验收场景翻译成**可看、可点**的屏幕，再让架构按这批屏幕去划模块与 seam。

**原型同时承担两个角色，缺一不可：**

| 角色 | 含义 | 不做的后果 |
|---|---|---|
| **视觉稿** | 高保真呈现最终观感：真实配色、字号层级、间距、圆角、图标、真实中文文案与示例数据 | 视觉决策被推迟到实现阶段，架构一改视觉全废；评审时各人对"长什么样"想象不一致 |
| **交互原型** | 可点击、能在屏与屏之间真实跳转，走完整流程（含空态、错误态、返回路径） | 流程断点要到实现完才被发现（"原来第二屏没有返回入口"） |

> 只有线框、没有视觉 → 不算完成；只有静态图、点不动 → 也不算完成。**两者同时满足才是本阶段的 DoD。**

## 2. 位置与边界（先划清，避免与相邻步骤打架）

| 关系 | 规则 |
|---|---|
| **上游 Spec（阶段 1）** | 原型每一屏、每个状态都必须能**倒查到** `01-需求/<批次>/用户故事-*.md` 的某条验收场景。倒查不到的屏 = 范围蔓延：要么补进 Spec 回闸门 a，要么删掉。 |
| **下游 Plan（阶段 3）** | 原型的**页面清单 + 交互状态 + 组件边界 + 视觉 token** 是架构设计的输入：屏 → 页面/组件，交互状态 → 状态模型，跨端一致的视觉语言 → 共享层契约候选。 |
| **本阶段的产出不等于生产代码** | 原型在"无真实数据、无错误处理、无无障碍"的约束下写成。实现阶段按架构**重新写**代码，原型只作**结构与观感的依据**，不直接抄。 |
| **与「丢代码原型」的分工** | 逻辑/状态模型拿不准时，可在**阶段 5** 用 `prototype` skill 的 LOGIC 分支跑一个丢弃型状态机原型；那是另一件事、另一个时机。本阶段只做界面原型。 |

## 3. 为什么用 HTML 做原型

四条硬理由，任一条都足以定这个技术选型：

1. **免构建、跨端同源**：单个 `.html` 双击即开。iOS 与 Android 工程师、产品、设计看的是**同一份文件**，不存在"你看的和我截的不一样"。
2. **可交互**：点按能跳屏、能切状态——比静态图更接近真实使用，因而更容易暴露流程断点。
3. **纯文本、可进 git、可被 Agent 读写**：原型与其他产物一样是**版本化文本资产**，能 diff、能回写、能进文档链路，也能被后续架构/实现阶段直接消费。
4. **零依赖渲染**：不需模拟器、不需签名、不需装 App，**评审成本接近 0**——闸门 p 才可能被真正执行而不是被跳过。

## 4. 方法论来源（本流程的依据）

本流程不是自创，是把三条成熟公开实践**裁剪到移动端原生开发**的场景：

| 来源 | 取它什么 | 在本流程的落点 |
|---|---|---|
| **Spec Kit**（GitHub 官方 spec-driven 工作流） | 把「Spec → Plan」当作**必须停下的边界**，Plan 前先产设计物再谈实现 | 原型独立成一步、独立成闸门 p，不与架构设计混在一起 |
| **obra/superpowers · `brainstorming/visual-companion.md`** | 只把「**看比读更清楚**」的问题交给浏览器；屏幕按**语义命名**逐屏推进、不复用文件名；用可复用构件搭界面；交互留档供后续引用 | 逐屏推进 + 语义命名 + 构件化 + 走查留档（**只取流程骨架**） |
| **Matt Pocock · `prototype`（UI 分支）** | **3 个结构上真正互斥的变体** + 一个切换器在同处切换 + `?variant=` 可分享；选定后并入实现、其余丢弃；原型是消耗品、要留档但不进主干 | 变体规则与切换器规范（见第 6 节）。**注意**：其"变体只比结构不比配色"的规则在本流程要放宽——本阶段要出视觉稿，视觉方向本身也是比较对象 |

## 5. 视觉稿规格（本阶段的核心要求）

**默认就是视觉稿级，不是线框级。** 灰盒占位块只允许出现在「尚未确定视觉方向」的个别局部，且必须在 `原型说明.md` 的「设计取舍」里说明原因。

### 5.1 保真度档位

| 档位 | 长什么样 | 何时用 |
|---|---|---|
| **V2 视觉稿（默认）** | 真实配色、字号层级、间距、圆角、图标、真实中文文案与示例数据；观感接近成品 | 本阶段默认，一切界面原型 |
| V1 视觉稿简版 | 视觉方向已有参照，但只画布局与主色，细节留空 | 仅当用户明确要求"先看布局" |
| V0 线框 | 灰盒占位 | **不用于本阶段**，仅在个别未定局部临时使用并说明 |

> 本阶段要求**精致且正确**。粗糙的线框不算完成本阶段。

### 5.2 设计 token 表（写在 `原型说明.md`，与 HTML 里的 CSS 变量一一对应）

视觉稿必须把"观感"落成**可被实现阶段照抄的数值**，否则只是"看着像"。至少覆盖：

| 类别 | 要列出的项 |
|---|---|
| 色彩 | 主色 / 主色浅底 / 背景 / 卡片面 / 分隔线 / 主文字 / 次文字 / 危险色 / 成功色（各给 hex） |
| 字号 | 大标题 / 标题 / 正文 / 辅助 / 角标（各给 pt 或 px + 字重） |
| 间距 | 页面边距 / 卡片内边距 / 列表行高 / 元素间距（各给数值） |
| 圆角 | 卡片 / 按钮 / 头像（各给数值） |
| 图标 | 用哪套（系统内置 / 自绘 SVG），出现在哪几个位置 |

> HTML 里这些值**必须**写成 `:root` 下的 CSS 自定义属性；`原型说明.md` 的 token 表与之一一对应。两端视觉语言不同的部分（见 5.3）分开列。

### 5.3 跨端视觉语言（本 skill 特有）

本 skill 面向 iOS / Android 双端，而两端系统视觉语言不同。原型需体现这一点：

- **两端都要的功能**：`原型图.html` 提供**平台开关**（iOS / Android），同一屏在两套视觉语言下分别渲染——
  iOS 侧用大标题导航 + 底部标签栏，Android 侧用 TopAppBar + 底部导航 + FAB 与 Material 圆角/高度。
  这直接把「跨端分叉点」画成可见的，架构阶段据此定共享层与落地分叉。
- **只做一端**：平台开关可不显示，按该端视觉语言渲染。
- **共享的部分**（信息层级、页面清单、状态集合、中文文案）**两端必须一致**，差异只在视觉语言与交互惯用法。

## 6. 变体与切换器（仅当视觉/结构方向真的没定时使用）

先一句话判断：

- 「这个页面**长什么样 / 怎么组织**还没定」 → 出 **3 个变体**（上限 5，再多从"差异"变"噪音"）。
- 「方向已定，只是画出来」 → **单变体**，别硬凑三个。

变体的硬规则：

1. **结构必须互斥**：不同布局、不同信息层级、不同主操作入口。三个只改圆角和蓝色的卡片网格**不是变体，是壁纸**。
2. **视觉方向也可以不同**：本阶段允许变体之间连配色/气质一起不同（这与第 4 节里 prototype skill 的原始取向不同，是本流程的放宽）。
3. **不能共用一个 Layout 外壳**：共用顶栏可以，共用整体版式就废了——每个变体要能自由丢弃版式。
4. **一个切换器在同处切换**：页内切换（不重开文件），当前变体写进 URL（`?variant=B`），保证**可分享、刷新不丢**。
5. **切换器自身必须显眼地"不属于设计"**：高对比药丸条 + 阴影，字号与配色**刻意与页面体系不同**。
6. **胜出后收束**：在 `原型说明.md` 的「设计取舍」写清**哪个变体胜出、为什么、从别的变体偷了哪一块**（真实决策常是"B 的头部 + C 的侧栏"），然后把落选变体从 `原型图.html` 删掉或折叠。

## 7. 状态覆盖清单（原型的核心价值，最易漏）

只画 happy path 的原型等于没画。**每一屏**都要过一遍下表，不适用的写「不适用」并给一句理由：

| 状态 | 要回答的问题 |
|---|---|
| **空态** | 一条数据都没有时，用户看到什么、被引导去做什么？ |
| **加载中** | 首次进入 / 长耗时的中态是什么？（进度条还是骨架屏？） |
| **有数据** | 正常态的信息密度与截断规则（超长标题怎么办）？ |
| **错误 / 拒绝** | 用户做了不被允许的事（格式不支持、权限拒绝、解析失败）时看到什么？ |
| **边界 / 越界** | 数据越界或历史数据失配时（如进度越界）如何回退、是否静默？ |
| **极值** | 0 条 / 1 条 / 很多条（是否需要滚动、分页、批量操作）？ |

> **倒查纪律**：把 `01-需求/<批次>/用户故事-*.md` 的验收场景逐条列出来，每条**指定一屏**作为载体。
> 有场景找不到载体 = 原型漏了；有屏找不到场景 = 范围蔓延。两者都必须在闸门 p 之前说清。

## 8. 命名规范（中文 + 功能语义）

产物名、目录名、屏 id、屏名**一律中文，且必须表达"这是哪个功能的哪一屏"**。

| 对象 | 规则 | 正例 | 反例 |
|---|---|---|---|
| 产物目录 | 中文，见 `任务拆解.md` 目录规范 | `02-原型/<批次>/` | `02-prototype/` |
| 产物文件名 | 中文，与 `templates/` 同名 | `原型说明.md`、`原型图.html` | `prototype-spec.md` |
| 屏 id（`data-screen`） | **中文语义名**，表达功能与状态，屏间不重名 | `书架-空态`、`书架-有数据`、`阅读器-正文`、`导入-格式被拒` | `screen1`、`div2`、`01`、`bookshelf-empty` |
| 屏名（列表里显示） | 中文，可与 id 相同或更口语化 | `书架（空）` | `Booklist Page` |
| 变体键 | 大写字母 + 中文括注 | `A（列表式）` | `variant-1` |

**屏 id 与 `原型说明.md`「页面清单」表的屏 id 必须逐字一致**——回写、对账、校验都靠它对齐。

## 9. 技术约束（可机检）

`原型图.html` 必须满足：

1. **单文件、零外部依赖、零构建**：不引 CDN、不外链字体/图片/JS 库；图标用内联 SVG 或字符。双击即开是硬要求。
2. **顶部固定「原型带」**：标注 `功能名 / 档位 / 生成时间 / 保真度`，并写明「这是原型，不是成品」，防止被误当真机截图。
3. **设备框**：iPhone 逻辑分辨率 **390 × 844**，内容区可滚动；多屏时并排或单屏切换。
4. **平台开关**（两端都要时）：`iOS / Android` 可切换，切换后整屏视觉语言随之变化。
5. **屏内导航**：给出**屏列表**（中文屏名）+ 上下屏切换；当前屏高亮。
6. **交互可点**：屏内的主操作按钮、列表项、返回入口都要真的能跳转（至少在原型内闭环）。
7. **必需标记**（校验器锚点）：
   - 根节点带 `data-prototype="<feature>"`；
   - 每个屏容器带 `data-screen="<中文屏id>"`；
   - 顶部原型带内含「原型」字样（人眼与脚本双重识别）。
8. **中文**：界面文案、注释、屏名一律中文。

| 产物 | 模板 | 必填章节 / 锚点 |

### 回写纪律（与 `代码文档同步.md` 同一套契约）

原型不是画完就定格：

- **阶段 2 内部**：走查发现屏/流程要改 → 直接改 `原型图.html`，差异记进 `原型说明.md`「走查记录」。
- **阶段 3 起**：若架构或实现阶段**被迫改动页面结构、屏数、交互状态或视觉 token**（新增一屏、合并两屏、砍掉某状态、换主色），
  必须**回写 `原型说明.md` 的「页面清单」「关键交互」「视觉稿规格」**，不允许只改代码不改原型文档。
- **阶段 6 一致性对账**会核「原型宣称赞 ↔ 实际实现」这一项，漂移项要么回写原型、要么回退代码。

## 11. 走查（闸门 p 的输入）

闸门 p 不是"看一眼觉得还行"，而是一次**逐屏走查**，结论写进 `原型说明.md`「走查记录」。走查表至少含：

| 屏 id | 覆盖的故事 / 场景 | 覆盖状态 | 结论 |
|---|---|---|---|
| `书架-空态` | US-2 浏览书架 | 空态 | 通过 / 待改 |
| … | … | … | … |

走查必须回答的四个问题：

1. **每屏都能倒查到故事吗？**（覆盖检查）
2. **每屏的状态覆盖齐了吗？**（空/加载/有数据/错误/边界/极值，对照第 7 节）
3. **跨端一致的部分画出来了吗？**（两端都要时：屏清单、状态集合、文案一致，只是视觉语言不同）
4. **有没有屏是"想当然"画出来的？**（与 Spec 冲突处必须当场指出，而不是留到实现阶段）

## 12. 反模式（出现即返工）

- **只画 happy path**：没有空态、没有错误态、没有拒绝路径。原型的价值恰恰在非正常路径。
- **交付灰盒线框**：本阶段要视觉稿，灰盒不算完成。
- **变体只差配色 / 文案**：这是调样式，不是比方案（视觉方向整体不同才算变体）。
- **把原型当生产代码抄进实现**：原型在低保真约束下写成（无真实数据、无错误处理、无无障碍），实现要按架构重新写，只把它当**结构、观感与交互的依据**。
- **命名敷衍**：`screen1` / `btn2` / 英文兜底 —— 后续无法回写、无法对账。
- **原型与实现漂移不回头改**：实现时改了屏却不回写 `原型说明.md`，文档变成谎言。
- **静态图冒充交互原型**：点不动、走不通流程，不算完成。
