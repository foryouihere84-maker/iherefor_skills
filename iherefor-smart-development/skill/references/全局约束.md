# 工程全局约束（Constitution）

> 本文件是**全局工程原则**——对所有功能普遍有效，不属于任何单个功能。在阶段 0（前置依赖检查）时加载，
> 后续每个阶段的决策都会回到本文件的约束上。
> 与 Spec Kit 的 Constitution 层对应；与技术栈、代码原则、禁止事项相关，具体可配置值仍以 `config/` 下 json 为准，
> 本文只承载「原则」，不重复「可配置值」。

## 1. 技术栈与平台基线（决定性约束）

- 端覆盖：**iOS / Android 原生**。本 skill 只管原生功能开发，不承载任何具体项目或外部 skill 的能力。
- 跨端共享的是「领域模型、数据契约、不变量」，**不是源码**；两端语言/框架不同，落地层各自实现、守住同一份契约。
  契约必须精确到**字面**：方法名、字段名、枚举取值与口径（时间/单位/精度/空值）两端对齐，
  **每一处两端字面差异都必须显式登记**，未登记的差异一律视为缺陷。规则集与出处见 `references/跨端共享.md`。
- 移动端 TDD 的测试栈、seam 深度、编译门槛以 `config/mobile-tdd.json` 与 `references/iOS测试约定.md` / `references/Android测试约定.md` 为准，
  **不得沿用语言无关的测试假设**（如 Node/TS 生态默认）。
- **界面共识先于架构**：需求确认后必须先产出并确认**视觉稿 + 交互原型**（`02-原型/<批次>/`），才进入架构设计。
  细则见 `references/原型绘制.md`。

## 2. 代码原则

- **seam 可测**：领域层 / 用例 / ViewModel 必测；依赖通过接口/协议注入，禁止在被测对象内部 `new` 具体依赖。
- **只测行为，不测实现**：断言外部可观察结果，不断言私有属性 / 内部调用顺序；seam 写测试前先确认。
- **编译是硬门槛**：iOS（Xcode）与 Android（Gradle）**分别**编译通过、0 error 才可交付，不得用一端推断另一端。
- **先搜事实、再设计**：架构方案依赖的"最佳实践/官方推荐"必须先经白名单（`config/trusted-sources.json` 的 L1+L2）搜索取证，
  结论附一手来源；L3 社区帖仅用于查 bug 反例，禁止作为架构决策依据。
- **文档驱动**：每个功能的产出物落到 `docs/<feature>/`，按「分类目录 + 入口导航」组织，照 `templates/` 填空，可被 `scripts/scan-artifacts.py` 机器核验。
- **命名中文且语义正确**：`docs/<feature>/` 下的目录名、产物文件名、原型屏 id 一律中文并表达真实功能语义，
  禁止英文名与序号/缩写兜底。机器面向的配置（`config/*.json`）与脚本保持英文。
- **代码与文档一致（反向同步）**：文档不是写完就定格——实现中改代码必须按 `references/代码文档同步.md` 回写对应文档章节
  （**含原型文档**：改了页面结构/屏数/交互状态/视觉 token 须回写 `原型说明.md`）；
  交付门前做一致性对账，漂移项要么回写文档、要么回退代码。**禁止让 `docs/<feature>/` 里的契约与实际代码相背离。**
- **`03-架构/` 是项目总体架构约束层（全局共享 + 增量更新）**：它不是「阶段 3 的产出物堆」，而是**全项目唯一的架构真相**，
  为所有批次共享、**不随需求分叉、不因批次新建**。两个方向的同步都是义务：
  ① 本层变更 → 同步 文档 + 代码 + 所有活跃批次的相关产物；
  ② 别处（代码 / `01-需求` / `02-原型` / `04-落地计划` / 本目录其他档）改动触及本层内容 →
  **本层必须同步增量修订**：只改受影响条目、不整篇重写，并在文末「增量更新记录」追加一行台账。
  **架构层失真会同时毒化所有批次**（下个批次读到的是过期约束、错误被继承而非被发现），故这是全项目里唯一
  被要求「留增量轨迹」的一层。规则见 `templates/模板说明.md` 第 1.2 节与 `references/代码文档同步.md` 第 2.1 节。
- **按规模分级，不是无差别满配**：功能按 `config/tier.json` 判据分 full/lite 两档；lite 档收缩闸门与产物，但**不放松约束**——
  保留 a/p/b/d + 交付门，收缩的是「仪式」而非「安全」。无论哪档，需求/原型/方案/实现四类关键决策都必须经人工确认，
  原型产物与一致性对账不因档位省略。

## 3. 禁止事项

- 禁止把「两端都要」当成「同一流程跑两遍、互不引用」——必须先定共享层再分叉。
- 禁止在需求/原型/方案/变更清单四关未获人工确认前写生产代码（闸门 a/p/b/c 未过，不得写码）。
- 禁止跳过原型直接进入架构设计——界面与流程未达成共识时，架构讨论没有依据。
- 禁止交付灰盒线框冒充原型——本 skill 的原型要求是**视觉稿 + 交互原型**。
- 禁止内联缺失 skill 的规则来「绕过」阶段 0 的依赖检查。
- 禁止把 `03-架构/` 当成「阶段 3 的一次性产出物」——它是**项目总体架构约束层**；禁止改了代码或上游文档
  却不增量回写架构层、不留台账（架构层漂移会被后续批次继承）。
- 禁止引用任何具体项目名、或耦合其它 skill 的能力作为本 skill 的方法论依据——本 skill 是独立通用编排器，规范用通用表述。

## 4. 全局约束与功能级决策的边界

以上是**全局**约束，只在重大决策变化时才改；单个功能的版本/平台/依赖选择属于该功能的 **Plan**（阶段 3/4），
不属于本文件。判断标准：**「换了功能是否依然成立」**——是 → 全局约束，否 → 功能级 Plan。
