# 任务级拆解（Task Breakdown）

> 本文件是 `iherefor-smart-development` 编排器的**任务级执行契约**。SKILL.md 主线只列阶段与闸门，
> 阶段内部每个任务的目标、输入、产出物、可机检 DoD、点名 skill 全部在此细化。
> 模型生成产物时**照 `templates/` 同名模板填空**，校验器 `scripts/scan-artifacts.py` 按模板必填章节核验。
>
> **分层原则**（对齐 Spec Kit 五层模型，保留移动端特色）：
> `全局约束（Constitution）→ 需求（Spec）→ 原型（Prototype）→ 方案（Plan）→ 任务（Tasks）→ 实现（Implementation）`
> 每一层向下移交，都要求上一层已经过人工确认。
>
> **原型层是本 skill 在 Spec Kit 之外增补的一层**：需求理清后、架构设计前，先把「用户看到的界面、视觉观感、
> 屏与屏怎么走」钉成**视觉稿 + 交互原型**，架构才有可见的依据。详见 `原型绘制.md`。

---

## 0. 分层模型与闸门总览

| 层 | 对应阶段 | 产出物 | 闸门 |
|---|---|---|---|
| **全局约束** Constitution | 阶段 0 前置 | `全局约束.md`（skill 内，非功能产物） | 项目级，一次确认 |
| **需求** Spec | 阶段 1 需求理清 | `01-需求/<批次>/*` | 🔒 a |
| **原型** Prototype | 阶段 2 原型设计 | `02-原型/<批次>/*` | 🔒 p |
| **方案** Plan | 阶段 3 架构设计 + 阶段 4 变更清单 | `03-架构/*`（**全局共享，无批次**）+ `04-落地计划/<批次>/变更清单-NN-<短名>.md` | 🔒 b（方案）+ 🔒 c1（变更清单） |
| **任务** Tasks | 阶段 4 的任务拆分 | `04-落地计划/<批次>/任务拆分.md` | 🔒 c2（独立） |
| **实现** Implementation | 阶段 5 TDD + 阶段 6 交付 | `05-实现与测试/<批次>/*` + `06-交付/<批次>/*` | 🔒 d + 交付门 |

> `<批次>` = `NN-<需求名>`（如 `01-阅读进度续读`），一次需求迭代一个批次目录。

**关键设计**：

1. **原型门（🔒 p）独立于架构门（🔒 b）**——先让用户确认"长什么样、怎么走"，再谈"代码怎么划模块"。
   两者混在一起做，等于用架构讨论掩盖界面分歧。
2. **`方案`（怎么做）与 `任务`（分几步做）是两个独立闸门 c1 / c2**——方案审阅架构决策与依赖，
   任务审阅「切分是否遗漏边界案例」。这是对齐 Spec Kit 的第三个"必须停下"点。
3. **架构层（`03-架构/`）全局共享、不随需求分叉**——架构是全项目的单一真相，所有批次都参考它做设计。
   它一旦改动，必须同步**文档 + 代码 + 所有活跃批次**的相关产物（见 `代码文档同步.md`）。

## 0.1 产出物目录规范（批次层 + 阶段分类目录 + 入口导航，校验器扫描基准）

所有阶段产物统一落到目标工程的 `docs/<feature>/` 下。目录名与产物文件名是
`scripts/scan-artifacts.py` 的扫描锚点，不得随意改名。**目录名与文件名一律中文，且须语义正确**。

### 两级结构：批次层 + 产物层（本规范的地基）

**需求不是唯一的。** 每做一次需求就是一轮完整迭代（需求 → 原型 → 架构 → 落地 → 实现 → 交付）。
各轮产物若混在同一目录，就只能靠在旧文档上「增增改改」——历史被抹掉，评审无法追溯。因此分两级：

| 层级 | 形态 | 序号语义 | 变更粒度 |
|---|---|---|---|
| **第一级：批次层** | 目录 `<NN-需求名>` | 「**第几次需求迭代**」 | 一次完整的 需求→交付 闭环 |
| **第二级：产物层** | 文件 `类型-NN-<短名>.md` 或 `类型.md` | 「**本轮之内的第几版**」 | 本轮内的一次修订 / 一次重跑 |

**新增一次需求 = 新建一个批次目录**，而不是在旧需求文档上增删改。

### 批次对齐规则（硬约束）

批次目录出现在 **5 个阶段**下，且**必须同名**：

```
01-需求/01-阅读进度续读/          02-原型/01-阅读进度续读/
04-落地计划/01-阅读进度续读/      05-实现与测试/01-阅读进度续读/
06-交付/01-阅读进度续读/
```

同名即对齐：从任一阶段的批次目录出发，都能找到本轮的全链路产物。
**校验器核验对齐性**——某阶段有该阶段目录但缺了同名批次目录，就报「批次未对齐」（说明漏跑了那个阶段）。

- 批次序号 `NN` 两位数字，从 `01` 起**连续递增**。
- 批次一旦交付即**冻结为历史快照**；后续修订走**新批次**，不回头改旧批次。
- 批次清单的**唯一权威索引**是 `00-入口/文档导航.md` 的「批次清单」表，新增批次必须在那里追加一行。

### 架构层例外：`03-架构/` 全局共享

`03-架构/` **不带批次目录**——架构是全项目共享的单一真相。所有批次都参考它做设计，
而不是每批次各存一份架构快照。同样无批次的还有 `00-入口/`（批次清单与总入口）与
`99-来源与日志/`（全程追加日志）。

> **架构改动 = 全项目同步**：`03-架构/` 任一产物变更后，必须同步 **文档 + 代码 + 所有活跃批次**
> 的相关产物（尤其各批次的 `跨端共享需求.md` / `领域模型.md` / `原型说明.md`）。
> 这条靠交付门的 `一致性对账-NN-<短名>.md` 卡住，见 `代码文档同步.md`。

### 产物二分类（批次内的命名与演进规则）

产物**先分两类，再定命名与核验规则**（总则见 `templates/模板说明.md` 第 2 节）：

| 分类 | 命名 | 演进方式 | 校验器识别 |
|---|---|---|---|
| **收敛型**（批次内） | `类型.md`，无序号单例 | 表达**本批次结束时**的当前真相，原地更新 | 路径无 `*` |
| **追加型**（批次内） | `类型-NN-<短名>.md`，NN 两位数字从 `00` 起连续 | **每次新增 → 新建下一个编号的文件**，历史文件不可变 | 路径含 `*` |

**追加型的 7 类产物**：需求、用户故事、变更清单、编译报告、审查报告、一致性对账、交付报告。
（批次内新增一版 = 新建 `需求-01-<短名>.md`，绝不在 `需求-00-<短名>.md` 上增删改。）

> **收敛型"每批次一份"为何不破坏单一事实源**：约定「当前真相 = **最新批次**的那一份」。
> 非首批次开工时应**先从上一批次同名文件继承**再演进；每个已交付批次各自冻结为当时快照。

### 目录树

```
<目标工程>/docs/<feature>/
├── 00-入口/                                          【全局单例】
│   └── 文档导航.md              # 批次清单 + 读取顺序 + 冲突优先级 + 分派口径  [收敛]
├── 01-需求/                                          【批次内】Spec 层
│   └── <批次>/                  # 如 01-阅读进度续读
│       ├── 需求-00-<短名>.md     # [追加] 新版本 → 新建 需求-01-<短名>.md…
│       ├── 领域模型.md          # [收敛] 术语 / 实体完整字段表 / 不变量 / 枚举取值语义（两档都产出，含单端）
│       ├── 用户故事-00-<短名>.md # [追加]
│       └── 跨端共享需求.md       # [收敛] 仅两端都要时；跨端契约事实源——命名(含双端字面映射)/接口/字段跨端核对/枚举跨端核对/口径/错误
├── 02-原型/                                          【批次内】Prototype 层
│   └── <批次>/
│       ├── 原型说明.md          # [收敛] 页面清单 / 关键交互 / 状态覆盖 / 视觉稿规格 / 设计取舍 / 走查记录
│       └── 原型图.html          # [收敛] 视觉稿 + 交互原型（单文件零依赖，双击即开）
├── 03-架构/                                          【项目总体架构约束层】全局单例（架构决策，全 [收敛]）
│   ├── 待查证问题.md                                    所有批次共享，无批次目录；
│   ├── 事实纪要.md                                      别处改动须同步增量更新并留台账
│   ├── 设计约束.md                                      （每份文末含「增量更新记录」）
│   ├── 候选方案.md
│   ├── 方案对比.md
│   ├── 跨端共享层.md             # 仅两端都要时
│   └── 方案草案.md              # 架构基线
├── 04-落地计划/                                      【批次内】Plan 层（变更清单）+ Tasks 层
│   └── <批次>/
│       ├── 架构审计.md          # [收敛]
│       ├── 变更清单-00-<短名>.md # [追加] ← 闸门 c1（每轮改动新建一个编号）
│       ├── 回滚方案.md          # [收敛]
│       └── 任务拆分.md          # [收敛] ← 闸门 c2（独立）
├── 05-实现与测试/                                    【批次内】Implementation 层
│   └── <批次>/
│       └── 测试计划.md          # [收敛] 测试代码/源码在各工程目录，不在此处
├── 06-交付/                                          【批次内】Implementation 层（收尾，全 [追加]）
│   └── <批次>/
│       ├── 编译报告-00-<短名>.md
│       ├── 审查报告-00-<短名>.md
│       ├── 一致性对账-00-<短名>.md # ← 交付门（代码↔文档对账，lite 不省略）
│       └── 交付报告-00-<短名>.md
└── 99-来源与日志/                                    【全局单例】
    └── 运行日志.jsonl            # 全程增量日志（时间戳 + 阶段快照）
```

- `<feature>` 用功能短名（如 `订阅管理`），由任务 1.1 定名并初始化目录。
- `<批次>` 用 `NN-<需求名>`（如 `01-阅读进度续读`），由任务 1.1 建立并写入批次清单。
- 每个产物文件**照 `templates/` 下同路径模板填空**，头部声明导航入口 + 所属阶段 + **所属批次** + **产物类型**。
- **两处序号都要连续**：批次序号 `01,02,03…`；批次内追加型序号 `00,01,02…`。
- 若任务产出物落在各工程目录（如测试代码、源码），校验器对该任务标「不判定」，由阶段 6.1 双端编译门兜底。
- 若无 `docs/<feature>/` 目录，校验器按「尚未开始」处理，仅提示。

### 运行日志.jsonl 约定（每条一行 JSON，落 `99-来源与日志/`）

```jsonl
{"ts":"2026-09-17T15:00:00+08:00","event":"new_batch","feature":"阅读应用","batch":"01-多格式书架与续读","tier":"full"}
{"ts":"2026-09-17T15:05:00+08:00","stage":2,"task":"2.2","batch":"01-多格式书架与续读","event":"done","artifact":"02-原型/01-多格式书架与续读/原型图.html","ok":true}
{"ts":"2026-09-17T15:06:00+08:00","stage":2,"task":"2.3","batch":"01-多格式书架与续读","event":"tier_change","from":"full","to":"lite","reason":"无跨端共享层"}
```

> 每条带批次的记录都应含 `batch` 字段；新建批次时记一条 `new_batch` 事件。

## 0.2 功能分级（tier）：full / lite

> 判据、闸门收缩、可跳过产物以 `config/tier.json` 为唯一数据源，本节只给任务级对应关系。
> 分级在**阶段 0 末尾**用「入口第一眼信号」判定，默认 `full`；阶段 1 结束允许升/降级一次。

| 档位 | 闸门序列 | 阶段 3 收缩 | 可跳过的任务/产物 |
|---|---|---|---|
| **full**（标准） | a → **p** → b → c1 → c2 → d → 交付门 | 全跑（搜索 + DESIGN-IT-TWICE 三案） | 无 |
| **lite**（轻量） | a → **p** → b → d → 交付门 | 仅 L1 参照需查证时搜一次，不做三案 | 见下表，标「lite 可跳过」的任务 |

**lite 档可跳过的任务**（对应 `tier.json` 的 `skip_artifacts`，校验器 `--tier lite` 时对它们标「已跳过」）：

| 任务 | 跳过产物 | 说明 |
|---|---|---|
| 1.5 定共享需求 | `01-需求/<批次>/跨端共享需求.md` | 一端即可，无需跨端共享需求 |
| 3.4 并行出多案 | `03-架构/候选方案.md` | 不做 DESIGN-IT-TWICE 三案 |
| 3.5 方案对比 | `03-架构/方案对比.md` | 同上，无多案可对比 |
| 3.6 定共享层 | `03-架构/跨端共享层.md` | 无跨端共享层 |
| 4.1 审现有架构 | `04-落地计划/<批次>/架构审计.md` | 纯增量改动，不审计既有架构 |
| 4.4 拆任务 | `04-落地计划/<批次>/任务拆分.md` | c2 并入 b，方案草案内载执行步骤 |

> 被跳过的产物**全是收敛型**——追加型（需求/用户故事/变更清单/交付记录）不因档位跳过编号，
> 批次对齐也不因档位放松（lite 档同样要在 5 个阶段建同名批次目录）。

> **lite 不是无闸门**：仍保留 a（需求）、**p（原型）**、b（方案，含变更清单+执行步骤的合并确认）、d（实现）+ 交付门。
> 收缩的是「仪式」不是「约束」——合并确认仍要求用户真正过一遍，而非直接放行。
>
> **原型层在 lite 档不省略、只收缩**：`原型说明.md` 与 `原型图.html` 两份产物**两档都要产出**（它承载的是界面决策，
> 属"约束"而非"仪式"），lite 档只收缩为**单变体 + 单平台**，不做多变体与跨端视觉语言并排。
>
> 阶段 3 内 `待查证问题.md` / `事实纪要.md` 在 lite 下虽未列入 skip_artifacts（可能有 L1 查证），
> 但编排器可按需裁剪：无需查证时这两份也可不产，此时校验器对它们按「缺失」提示，属可接受的降级。

## Spec 层 — 阶段 1 需求理清（🔒 闸门 a）

> 目标：把「一句需求」变成「产品+技术共同确认的功能规格」。重点产出 **Out of Scope 与边界案例**（防 Agent 擅自扩范围）。

| # | 任务 | 做什么 | 输入 | 产出物 | 可机检 DoD | 点名 skill |
|---|---|---|---|---|---|---|
| 1.1 | 定功能短名 | 定 `<feature>` 短名并初始化目录 + 入口导航 | 用户原始诉求 | `99-来源与日志/运行日志.jsonl`、`00-入口/文档导航.md` | log 含 `feature` 字段；导航文件存在 | — |
| 1.2 | 厘清需求边界 | 明确「做什么/不做什么 Out of Scope」+ 边界案例 | 原始诉求 | `01-需求/<批次>/需求-NN-<短名>.md` | 含「业务目标」「边界」「非目标」章节 | `grilling` |
| 1.3 | 固化领域模型 | 术语定义、实体**完整字段表**（语义/类型口径/可选性/约束/默认值）、不变量、枚举取值语义 | 需求说明 | `01-需求/<批次>/领域模型.md` | 含「术语表」「实体」「不变量」「枚举与取值域」章节；每个实体字段表六列齐全；不变量带编号且写明违反行为 | `domain-modeling` |
| 1.4 | 出用户故事+验收场景 | 可验收故事列表（GWT 验收场景） | 需求+领域模型 | `01-需求/<批次>/用户故事-NN-<短名>.md` | 含「用户故事」「验收场景」章节 | `to-questionnaire` |
| 1.5 | 定共享需求 | 两端都要时抽跨端契约：共享/分叉边界 + 命名规范（禁止同义词 / **双端字面映射**）+ 接口规范（方法名/入参/出参/失败）+ **字段跨端核对**（线格式/双端差异）+ 枚举跨端核对（线格式/未知值处理）+ 口径铁律 + 错误语义。**只登记跨端维度，不重抄领域模型** | 前序全部（尤其 `领域模型.md`）+ `references/跨端共享.md`（命名与契约规则集） | `01-需求/<批次>/跨端共享需求.md` | 含「共享范围」「命名规范」「共享接口规范」「共享数据契约」「枚举与取值域」「跨端一致性铁律」「分叉点」章节；**双端字面差异全部登记**（未登记者视为缺陷）；不变量引用领域模型编号而非重抄；一端可省 | `grilling` |

🔒 **闸门 a**：需求理解正确（含 Out of Scope、边界案例）获确认，才进入原型层。

## Prototype 层 — 阶段 2 原型设计（🔒 闸门 p）

> 目标：把已确认的需求翻译成**视觉稿 + 交互原型**——看得见（真实配色/字号/间距/中文文案）、点得动（屏与屏真实跳转）。
> 细则（含保真度档位、设计 token、跨端视觉语言、命名规范、反模式）见 `原型绘制.md`，动手前必读。
>
> **倒查纪律**：每屏必须能倒查到 `01-需求/<批次>/用户故事-*.md` 的某条验收场景；有场景无屏 = 漏画，有屏无场景 = 范围蔓延。

## 同源契约的维护（四份文件必须同步）

本文件「产出物」列、`templates/` 的模板与清单、`templates/模板说明.md` 第 5 节表、`scripts/scan-artifacts.py` 的 `DEF` 常量
是**同一份机检契约的四种表述**——改了任一处都必须同步其余三处，否则校验会「假绿」。

```
       references/任务拆解.md  ←── 人读的任务契约（产出物列）
                ↕
   templates/模板说明.md 第5节  ←── 人读+模型读的映射表（类型+锚点）
                ↕
      templates/ 实际模板文件  ←── 产物空壳（二级标题=锚点来源，权威）
                ↕
   scripts/scan-artifacts.py DEF ←── 机器读的基准（产物路径 glob + 锚点）
```

**改完任一处，跑一次核验器**：

```bash
python3 scripts/check-consistency.py      # 在 skill/ 目录下
```

它做四向对照（含模板缺失 / 孤儿模板 / 类型标注 / 锚点漂移 / 清单遗漏 / 任务拆解遗漏），任一处漂移即非零退出。

**追加型产物的表述差异（不是漂移）**：`DEF` 用 glob（`需求-*.md`，脚本要匹配多实例），人类文档用
`需求-NN-<短名>.md`（人看得懂）。核验器对这两种写法做归一化。
