# 跨端共享层规范

当需求同时要 iOS 与 Android 两端落地时，本文件约束「什么必须共享、什么必须分叉」，并给出
**命名与接口契约的权威规则集**（阶段 1 `跨端共享需求.md` 与阶段 3 `跨端共享层.md` 都以本文件为规则来源）。

## 核心原则

**共享的是事实与契约，不是代码。** 两端语言/框架不同，不可能（也不应）共享源码；
共享的是「不会因平台而变」的那部分，落地层各自实现并守住同一份契约。

**契约必须精确到「字面」。** 只说「两端字段含义一致」是不够的——含义一致但拼写不同（`coverUrl` / `coverURL` / `coverImage`）
在实现期就是漂移。所以：**每一处两端字面差异都必须显式登记，未登记的差异一律视为缺陷。**

## 必须共享（单一事实源）

1. **需求与用户故事**：actor / feature / benefit 两端完全一致。同一份 spec，一次确认，两端共用。
2. **领域模型**：实体、值对象、状态机的语义定义一致。命名、字段含义、不变量在两端的领域层**等价**（不是字节级相同，而是语义一致）。
3. **数据契约**：API 请求/响应结构、本地存储 schema、跨端交互的字段类型与默认值必须一致。
   一处改，两端同步（这是「共享层」最硬的约束）。
4. **边界与规则**：输入校验规则、业务不变量、错误码语义，两端一致。
5. **接口签名与命名**：同一能力的**方法名、参数名、字段名、枚举取值**两端对齐（细则见下节）。
6. **口径**：时间、单位、精度、文本比较、空值语义——跨端 Bug 的高发区不是逻辑而是口径（细则见下节）。

## 必须分叉（平台各自落地）

1. **UI 与技术栈**：iOS 用 SwiftUI/UIKit，Android 用 Compose/View；布局、生命周期、导航各自实现。
2. **平台能力接入**：网络库、数据库 ORM、依赖注入框架、权限申请、推送等走各自平台惯用法。
3. **测试栈**：见 `config/mobile-tdd.json` 的 ios_defaults / android_defaults。
4. **资源与性能策略**：内存上限、线程模型、缓存淘汰策略按平台能力各自定，但**对外行为须符合共享契约**。

## 命名与接口契约规范（可执行规则）

> **默认遵循下列公开规范；本项目要覆盖默认值时必须写明理由**，并登记进 `跨端共享需求.md` 的「命名规范」节。
> 出处：[AIP-140](https://google.aip.dev/140)（字段）· [AIP-126](https://google.aip.dev/126)（枚举）·
> [AIP-190](https://google.aip.dev/190)（总则）· [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) ·
> [Kotlin Coding Conventions](https://kotlinlang.org/docs/coding-conventions.html)。

### 命名基线

| 规则 | 反例 → 正例 | 出处 |
|---|---|---|
| 类型/协议 UpperCamelCase；字段/方法/参数/变量 lowerCamelCase | `book_format` → `bookFormat` | Swift / Kotlin |
| 编译期常量 SCREAMING_SNAKE_CASE | `maxRetryCount` → `MAX_RETRY_COUNT` | Kotlin |
| 字段名必须是名词，不得是动词或动作意图 | `disable` → `disabled` | AIP-140 |
| 布尔字段省略 `is` 前缀（与保留字冲突才加） | `isDisabled` → `disabled`；`new` → `isNew` | AIP-140 |
| 集合用复数、单值用单数 | `bookList` → `books`；单值 `books` → `book` | AIP-140 |
| 字段名不得含介词 | `reasonForError` → `errorReason` | AIP-140 |
| 形容词前置 | `itemsCollected` → `collectedItems` | AIP-140 |
| 广为人知的缩写优先用缩写 | `configuration` → `config`；`identifier` → `id` | AIP-140 |
| 单位缩写紧贴数值语义 | `distanceKilometers` → `distanceKm` | AIP-141 |
| 时间点字段以 `Time` 收尾 | `createdAt` → `createTime` | AIP-142 |
| 通用资源标识用 `uri`，仅网址用 `url` | `link` → `uri` / `url` | AIP-140 |
| 人类可读名用 `displayName`；正式名用 `title` | `name` → `displayName` | AIP-140 |
| 字段名不得与所在类型同名 | `Book.book` → `Book.title` | AIP-140 |
| 不得以数字开头、不得有前导/尾随/连续下划线 | `2faEnabled` → `twoFactorEnabled` | AIP-140 |
| 禁止无意义词 `Manager`/`Helper`/`Util`/`Wrapper`/`Impl` | `BookManager` → `BookShelf` | Kotlin |
| 方法名 = 动词 + 名词，读起来是一句话 | `doImport` → `importBook` | AIP-190 |
| 有副作用用祈使动词；无副作用用名词短语或 `-ed`/`-ing` | `sort` / `sorted` | Swift |
| 工厂方法以 `make` 开头 | `createParser` → `makeParser` | Swift |
| 布尔返回的方法读作对接收者的断言 | `checkEmpty` → `isEmpty` | Swift |
| 禁止 `do*`/`handle*`/`process*`/`perform*` 无信息量前缀 | `handleImport` → `importBook` | Kotlin |

### 双端字面映射（最容易出错的点）

**线格式名（序列化名）是权威拼写；两端代码属性名是它的语言派生形式。**

| 语言 | 缩写大小写规则 | 例（权威名 `coverUrl`） |
|---|---|---|
| Swift | 在美式英语中通常全大写的缩写，按所在位置**统一**大小写（全大写或全小写）；其余缩写当普通词 | `coverURL` |
| Kotlin | **2 字母缩写全大写；超过 2 字母仅首字母大写** | `coverUrl`；（`IO`→`IOStream`，`Xml`→`XmlFormatter`） |
| 线格式 | 统一 camelCase（本项目口径，两端一致） | `coverUrl` |

**强制登记**：凡两端字面不同者（如上例的 `coverURL` / `coverUrl`），必须在 `跨端共享需求.md` 的
「双端字面映射」表登记；未登记的差异视为缺陷。平台类型遮蔽导致的改名（如 Swift 的 `Data`/`URL`）
同样必须登记。

### 字段契约五要素

每个共享字段必须同时给出，缺一不可：**名字 · 类型口径 · 可选性 · 取值约束 · 默认值**。

- **类型口径**用跨语言中立词（字符串 / 整数 / 浮点 / 布尔 / 时间点 / 时长 / 枚举 / 列表<…> / 可选<…> / 字节串 / 标识），
  不得直接写 `String` / `val` / `Optional` 等语言类型。
- **可选性三态**：必填 / 可空（存在且语义为"无"）/ 有默认值（缺省时取默认）。禁止靠"约定"。
- **禁止用哨兵值表示"无"**：空字符串、`0`、`-1`、`"N/A"` 都不算"无"，必须用可选。
- **新增字段必须自带默认值语义**：老数据反序列化后不得崩，行为须等价于"字段不存在"。

### 枚举取值规范（对齐 AIP-126）

- 枚举**必须有一个"未指定/未知"取值**作为默认值；枚举不得只有一个取值。
- 线格式取值用 UPPER_SNAKE_CASE 或单词小写，**两端必须一致**（本项目二选一后写进契约）。
- **每个枚举必须写明「未知值处理」**：遇到本端不认识的新取值，是降级、忽略还是拒绝。这条不写，两端在
  "新版本数据被老版本读到"时行为必然不一致。
- 取值一经发布**不得改语义、不得复用**；删除的取值永久保留为"已废弃"。
- 每个枚举须标注**「冻结」或「可增长」**；可增长须说明追加节奏上限。

### 口径铁律（跨端口径不统一 = 必然出 Bug）

两端必须逐条定死，不允许"到时候看"：

| 维度 | 必须写明的内容 |
|---|---|
| 时间点 | 时区（建议 UTC）、存储格式、精度（秒/毫秒） |
| 时长 | 单位（秒/毫秒/分钟） |
| 数值精度 | 小数位数、舍入规则、比较方式（禁止浮点直接比较相等） |
| 单位 | 字节/KB/MB；公制/英制 |
| 百分比与进度 | 区间、端点是否含、"未开始/已完成"如何表达 |
| 文本编码 | 编码、规范化形式（NFC/NFD） |
| 文本比较 | 大小写敏感性、collation、空白与全半角 |
| 空值语义 | 三态：不存在 / 存在但为空 / 存在且有值 |
| 集合顺序 | 有序/无序 + 排序键 |
| 数值边界 | 最大/最小值、溢出与越界回退规则 |

## 契约变更的影响面

共享契约是**跨端、跨批次**的公共资产，改动成本远高于单端代码：

- **本文件与 `跨端共享需求.md` 都是收敛型**——原地更新，不建版本文件。
- 但**已交付批次的契约变更会波及后续批次**：必须回到「批次清单」评估影响面，不得只在本批次内改完就宣布完成。
- `03-架构/` 随之变更时，走**全项目同步**流程（文档 + 代码 + 所有活跃批次的相关产物）。
- 加字段/加枚举取值允许直接加（须自带默认值语义）；改类型/单位/语义**不得原地改**，走新字段或新批次。
- 影响面评估与结论由交付门 `06-交付/<批次>/一致性对账-NN-<短名>.md` 卡住。

## 落地产物

- 阶段 1 结束前产出 `01-需求/<批次>/跨端共享需求.md`：共享/分叉边界 + 命名规范（含双端字面映射）+ 接口规范 + 字段跨端核对 + 枚举跨端核对 + 口径铁律 + 错误语义。
- 阶段 3 产出 `03-架构/跨端共享层.md`：把上述契约落到工程结构（模块边界、依赖方向、序列化实现）。
- 两端落地代码各自独立，但**必须能通过同一份共享契约文档做到逐字/逐语义对齐**。

### 三份文件的分工（不要互相重抄）

| 文件 | 回答 | 产出条件 | 事实源范围 |
|---|---|---|---|
| `01-需求/<批次>/领域模型.md` | **领域里有什么** | 两档都产出（含单端） | 字段的**语义与类型**、术语、不变量、枚举取值语义 |
| `01-需求/<批次>/跨端共享需求.md` | **两端怎么写才一致** | 仅两端时产出 | 凡涉及"两端"的约束（**跨端契约的事实源**）：字面映射、调用姿势、口径、错误对齐、兼容策略 |
| `03-架构/跨端共享层.md` | 这些契约**在工程里怎么组织** | 仅两端时产出 | 模块边界、依赖方向、序列化与存储实现 |

**跨端共享需求 ≠ 领域模型的重抄**：前者只登记跨端维度（线格式名、双端字面、双端差异、跨端一致性要求），
语义与类型由后者持有；不变量只**引用编号**（`V1`、`V2`），不复制条文。
判据口诀：**这句话单端也成立吗？** 是 → 领域模型；只有两端才有意义 → 跨端共享需求。
冲突时先改跨端档，再回写领域模型，不允许只改一边。详见 `templates/模板说明.md` 第 2.1 节。

## 反例（禁止）

- 两端各自写一份不同的领域模型，字段名/语义漂移。
- API 契约只在某一端写死，另一端「照着感觉」重造一份。
- 把「两端都要」当成「同一流程跑两遍、互不引用」。
- 契约只写"语义一致"而不登记双端字面映射——含义对了拼写不同，实现期照样漂移。
- 枚举不留"未知值"分支，新版本数据让老版本崩。
- 用哨兵值（空串/`0`/`-1`）冒充"无"。
