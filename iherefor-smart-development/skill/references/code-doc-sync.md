# 代码 ↔ 文档同步契约（Code-Doc Sync）

> 文档驱动开发最危险的失败模式不是「没有文档」，而是**文档与代码漂移**——代码是活物、文档是快照，
> 写在 `docs/<feature>/` 里的领域模型 / 数据契约一旦没跟上实现，就会变成「谎言」，下一个接手者基于错误假设做改动。
>
> 本文件定义**「工程 → 文档」的同步契约**：哪些代码改动、必须回写哪份文档、以及交付前如何对账。
> 定位是**治理式纪律 + 交付门对账**（不做代码解析自动比对，靠硬规则 + 可机检对账产物兜底）。

---

## 1. 核心原则（先立规矩）

1. **代码是 truth，文档是契约的投影**。任一时刻，「代码实际怎么做」与「文档宣称怎么做」不一致时：
   - 若代码是**有意偏离**已确认的文档 → 必须先回到对应闸门（a/b/c）重新确认，不能静默改码。
   - 若代码是**实现过程中的正确结果**（比如合并了字段、补了边界）→ **必须回写文档**，让文档跟上代码。
2. **改代码 = 改文档**，两步绑定，不允许只改其一。这是实现阶段的硬纪律，不是可选动作。
3. **对账在交付门强制做**：阶段 5 交付前，必须产出「一致性对账」产物，逐项核对「文档宣称 ↔ 代码实现」，
   漂移项要么回写文档、要么回退代码，不允许「带着漂移交付」。

---

## 2. 同步点映射表（改哪些代码 → 回写哪份文档哪一节）

这是本契约的执行核心。实现阶段（阶段 4）每改一处代码，先查下表，命中即回写对应文档章节：

| 代码侧的改动 | 必须回写的文档产物 | 回写到哪个章节 | 说明 |
|---|---|---|---|
| 新增/删除实体、字段、值对象 | `01-需求/domain-model.md` | 「实体」「术语表」 | 字段变了术语未必变，注意两处都要核 |
| 领域规则/不变量变化（校验、边界） | `01-需求/domain-model.md` | 「不变量」 | 常量变了要让文档里的不变量跟上 |
| 跨端共享结构/字段/类型/默认值变化 | `02-架构/shared-layer.md` | 「数据契约」「领域模型」「不变量清单」 | 两端都要时最硬，改一端必须核另一端 |
| 公开接口签名 / 导航 / 资源改动 | `03-落地计划/change-list.md` | 「签名/导航/资源变更」 | 与闸门 c1 的变更清单对齐 |
| 新增/升级第三方依赖 | `03-落地计划/change-list.md` | 「依赖」 | 含版本号 |
| 需求范围内外变化（补了边界案例 / 扩了范围） | `01-需求/requirements.md` + `01-需求/user-stories.md` | 「边界」「非目标」「验收场景」 | 扩范围禁止静默，必须回闸门 a |
| 测试计划外新增/删掉的测试 seam | `04-实现与测试/test-plan.md` | 「seam」「should 用例」 | 保证测试计划与真实测试一致 |

> **回写粒度**：文档里的实体/字段/不变量，应与代码中的对应声明**同名一致**（移动端允许语言级不同，
> 但语义与命名要对得上，尤其跨端时字段名必须同义）。

---

## 3. 交付门的一致性对账（硬步骤）

阶段 5 交付门（在 `code-review` 与产出交付报告之间）必须做一次「代码 ↔ 文档」对账，产出
`05-交付/一致性对账.md`（照 `templates/05-consistency-check.md` 填空）。对账基线 = 阶段 2/3 已确认的契约文档。

对账逐项走这三类，任一「未同步」项都要当场处理：

| 判定 | 含义 | 处理 |
|---|---|---|
| ✅ 已同步 | 文档与代码一致 | 记录 PASS |
| ⚠️ 漂移 | 代码变了、文档没跟上 | **回写文档**后记为已同步；若代码是错误实现则回退代码 + 回闸门 |
| ❓ 需复核 | 不确定是否漂移（如动态性强的语言） | 标出、人工确认，不默认放行 |

> **对账是本契约的「落地支点」**：不靠人自觉记得同步，而是靠交付门前这一步**把漂移暴露出来**。
> `scan-artifacts.py` 会把 `05-交付/一致性对账.md` 作为阶段 5 的必填产物卡住（含「同步点」「漂移项」章节），
> 缺了就无法通过结构校验。

---

## 4. 与现有机制的关系（不重复、不冲突）

- **单向「文档 → 工程」**（现有）：闸门 a/b/c 保证写码前有文档；本契约补上**反向「工程 → 文档」**，形成闭环。
- **校验器分工**：`scan-artifacts.py` 只查「对账产物存在 + 章节在场」，不做代码↔文档的语义比对——
  语义对账由交付门的人工/模型步骤完成，写入对账产物。避免把「查漂移」做成不靠谱的代码解析。
- **lite 档**：对账步骤**不因档位而省略**（这是约束不是仪式），但 lite 档对账覆盖的同步点按 `tier.json`
  收缩后的产物集执行（即只对账仍然产出的那份文档）。

---

## 5. 何时本契约会被触发

- 阶段 4（实现）每改一处代码 → 触发「同步点映射」回写。
- 阶段 5（交付）交付门前 → 触发「一致性对账」产出对账产物。
- 阶段 6（反馈）回跳重跑 → 若回跳原因是「漏同步」，回到对应对账项补写。
