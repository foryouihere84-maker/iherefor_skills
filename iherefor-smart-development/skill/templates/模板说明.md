# 文档模板体系（移动端版）

> 本文档定义 `iherefor-smart-development` 的产物文档模板规范。它采用**文档驱动开发**的做法：
> 把大型开发流程拆成「固定结构的文档产物」，每个产物有明确必填章节，可被脚本机器核验——将这套
> 通用方法论适配成 **iOS / Android 移动端**语义。
> 每个阶段的每个产出物都对应 `templates/` 下的一份模板；模型生成产物时**照模板填空**，
> 校验器 `scripts/scan-artifacts.py` 按模板的「必填章节」核验字段齐全。
>
> **命名规范**：`templates/` 下的模板名与 `docs/<feature>/` 下的产物名**一律中文且语义正确**，
> 禁止英文名与序号/缩写兜底（如 `原型图.html` 而非 `prototype.html`）。产物再叠加
> 「批次目录 + 类型-序号-短名」前缀（见第 2、3、4 节）。

---

## 0. 文档驱动要素的映射

文档驱动开发的核心是「固定结构 + 可机检 + 双向索引」。下表给出各要素在**通用后端服务开发**与本
skill（移动端）之间的语义对应，说明本 skill 如何把结果/产物组织成可核验的文档：

| 通用要素（后端服务开发的典型产物） | 本 skill（iOS/Android 移动端） | 说明 |
|---|---|---|
| 业务目标 / 业务边界 | 业务目标 / 边界 | 保持 |
| BDD 交互流程（Given/When/Then） | **用户故事 + 验收场景**（GWT 同构） | 移动端更强调"用户可见行为" |
| 接口（路径/请求/响应/错误码） | **领域模型 + 数据契约（跨端共享）** | 移动端无 HTTP 接口，核心是领域语义 |
| 元数据（表结构/缓存 Key/枚举） | **状态模型 + 持久化契约（本地存储 schema）** | 表→本地存储/DB schema |
| 原型稿 / 视觉稿 | **视觉稿 + 交互原型**（`02-原型/<批次>/`） | 移动端界面即产品，界面共识必须先于架构落定 |
| 服务实现（Controller/Service/Mapper） | **模块划分 + seam 位置（可测性）** | 移动端核心是可测 seam |
| 兼容策略 | 兼容策略（平台版本/schema 迁移） | 保持 |
| 单元测试（shouldXxx 用例表） | **测试计划（should 用例 + seam/Mock/断言）** | 保持 should 命名 |
| 完成标准 | 完成标准（DoD） | 保持 |

> 结论：保留文档驱动开发的**机制**（固定结构 + 可机检 + 双向索引），**内容**换成移动端领域语义。
> **原型层（Prototype）是本 skill 在通用模型之外增补的一层**，见 `references/原型绘制.md`。

## 1. 两级结构：批次层 + 产物层（本体系的地基）

**需求不是唯一的。** 每做一次需求就是一轮完整迭代（需求 → 原型 → 架构 → 落地 → 实现 → 交付）。
如果各轮产物混在同一个目录里，就只能靠在旧文档上「增增改改」——历史被抹掉，评审无法追溯，
旧结论与新代码对不上。

因此本体系立**两级结构**：

| 层级 | 形态 | 序号语义 | 变更粒度 |
|---|---|---|---|
| **第一级：批次层** | 目录 `<NN-需求名>` | 「**第几次需求迭代**」 | 一次完整的 需求→交付 闭环 |
| **第二级：产物层** | 文件 `类型-NN-<短名>.md` 或 `类型.md` | 「**本轮之内的第几版**」 | 本轮内的一次修订 / 一次重跑 |

**新增一次需求 = 新建一个批次目录**，而不是在旧需求文档上增删改。

### 1.1 批次对齐规则（关键约束）

批次目录出现在 **5 个阶段**下，且**必须同名**：

```
01-需求/01-阅读进度续读/
02-原型/01-阅读进度续读/          ← 同名 = 同一次需求
04-落地计划/01-阅读进度续读/
05-实现与测试/01-阅读进度续读/
06-交付/01-阅读进度续读/
```

同名即对齐：从任一阶段的批次目录出发，都能找到本轮的全链路产物。
**校验器会核验对齐性**——某阶段缺了同名批次目录就报错（说明这一轮漏跑了那个阶段）。

- 批次序号 `NN` 两位数字，从 `01` 起**连续递增**。
- 批次一旦交付即**冻结为历史快照**；后续修订走**新批次**，不回头改旧批次。

### 1.2 架构层例外：`03-架构/` = 项目总体架构约束层

`03-架构/` **不带批次目录**。它不是「阶段 3 的产出物堆」，而是**本项目的项目级架构约束层**——
所有批次都参考它做设计，而不是每批次各存一份架构快照。

两个必备性质：

| 性质 | 含义 | 落地机制 |
|---|---|---|
| **全局共享** | 全项目**唯一**的架构真相，跨批次、跨需求共享；**不随需求分叉，不因批次新建** | 路径无 `<批次>`；`scan-artifacts.py` 只核验一次 |
| **增量更新** | 别处（代码 / `01-需求` / `02-原型` / `04-落地计划` / 本目录其他档）改动触及本层内容时，**本层必须同步增量修订** | 每份产物文末「增量更新记录」台账，且作为**机检锚点**——缺则该产物校验不过 |

「增量更新」的准确含义：**只修订受影响条目，不整篇重写**；每次同步在台账追加一行
（日期 / 触发来源 / 本文件更新了什么 / 影响批次 / 关联产物）。这样既是「当前真相」单例，又留下可追溯的增量轨迹。

> **双向同步，不是单向**：
> - **本层 → 别处**：`03-架构/` 任一产物变更 → 必须同步 **文档 + 代码 + 所有活跃批次**的相关产物
>   （尤其各批次的 `跨端共享需求.md` / `领域模型.md` / `原型说明.md`）。
> - **别处 → 本层**：代码或上游文档变了 → 本层对应条目须**增量更新**并留台账。
>
> 两个方向都靠交付门的 `一致性对账` 卡住，见 `references/代码文档同步.md`。

同样无批次的还有 `00-入口/`（批次清单与总入口）与 `99-来源与日志/`（全程追加日志）。

### 1.3 三种作用域

| 作用域 | 包含 | 路径特征 | 核验方式 |
|---|---|---|---|
| **批次内** | `01-需求` / `02-原型` / `04-落地计划` / `05-实现与测试` / `06-交付` 下的产物 | 路径含 `<批次>` 层 | 逐批次核验 + 批次对齐核验 |
| **全局单例** | `00-入口/`、`03-架构/`、`99-来源与日志/` | 路径无 `<批次>` 层 | 只核验一次 |
| **工程目录** | 测试代码、源码 | 不在 `docs/` 下 | 不判定，由阶段 6.1 编译门兜底 |

## 2. 产物二分类：追加型 / 收敛型

在**批次之内**，产物再分两类——同一个批次会不断产生新的修订与新的执行记录，
它们**绝不能在原文件上增删改**（否则历史被抹掉、评审无法追溯、旧结论与代码对不上）：

| 分类 | 本质 | 命名 | 演进方式 | 校验器识别 |
|---|---|---|---|---|
| **追加型**（批次内） | 一次决策/一次执行留下的**不可变记录** | `类型-NN-<短名>.md`，NN 两位数字从 `00` 起 | 每次新增 → **新建下一个编号的文件**；历史文件**只读不可变** | 路径含 `*`（多实例 glob） |
| **收敛型**（批次内） | 描述「**本批次结束时是什么**」，被本轮后续产物持续改写 | `类型.md`，**无序号单例** | 上游一变就**原地更新**，不另建版本文件 | 路径无 `*`（单实例） |

**判定口诀**：问「这条记录以后还需不需要原文保留？」
- 需要 → 追加型（例：需求、用户故事、变更清单、编译/审查/一致性对账/交付报告）。
- 不需要，只要"当前最新" → 收敛型（例：领域模型、原型说明、任务拆分、测试计划）。

**追加型的 7 个产物**：

| 类型 | 产物路径模式（`<批次>` 省略） | 为什么追加 |
|---|---|---|
| 需求 | `01-需求/<批次>/需求-NN-<短名>.md` | 本轮新需求是**新事件**，不能在旧需求上增删改 |
| 用户故事 | `01-需求/<批次>/用户故事-NN-<短名>.md` | 故事随需求版本走，历史版本须可追溯 |
| 变更清单 | `04-落地计划/<批次>/变更清单-NN-<短名>.md` | 每次改动是独立审批单元（闸门 c1） |
| 编译报告 | `06-交付/<批次>/编译报告-NN-<短名>.md` | 每次编译是一次事实快照 |
| 审查报告 | `06-交付/<批次>/审查报告-NN-<短名>.md` | 每轮审查结论不可覆盖 |
| 一致性对账 | `06-交付/<批次>/一致性对账-NN-<短名>.md` | 每次对账记录漂移基线 |
| 交付报告 | `06-交付/<批次>/交付报告-NN-<短名>.md` | 每次交付独立留档（含回滚状态） |

**收敛型**（16 个）：批次内 8 个（`领域模型.md`、`跨端共享需求.md`、`原型说明.md`、`原型图.html`、
`架构审计.md`、`回滚方案.md`、`任务拆分.md`、`测试计划.md`）+ 全局单例 8 个（`文档导航.md` 与 `03-架构/` 全部 7 份）。

> **收敛型为什么能"每批次一份"而不破坏单一事实源**：约定「**当前真相 = 最新批次的那一份**」。
> 非首批次开工时应**先从上一批次同名文件继承**再演进；每个已交付批次各自**冻结为当时快照**。
> 这样既有清晰的历史链，又始终只有一个"最新真相"。

> **为什么不是所有产物都加序号**：序号只对"事件流"有意义。给收敛型产物编号会造成"多份当前真相"
> 的歧义（到底哪份是当前？），反而破坏单一事实源。**序号是历史的刻度，不是文件的装饰。**

> **`03-架构/` 的 7 份收敛型是特例但非例外**：它们同样是「当前真相」单例，但因为属于**项目总体架构约束层**，
> 额外要求**增量更新并留台账**——收敛型只说明「不编号、不另建版本文件」，不排除文内留增量记录。
> 台账见各模板末尾「增量更新记录」一节，规则见第 1.2 节。

### 2.1 分工纪律：`领域模型.md` ↔ `跨端共享需求.md` ↔ `03-架构/跨端共享层.md`（易重复，须严格遵守）

阶段 1 的 `领域模型.md`、`跨端共享需求.md` 与阶段 3 的 `03-架构/跨端共享层.md` 都会写到同一批实体与字段，
是**最容易被写成互相重抄**的一组。按**列**分工，不按**行**重复：

| | `领域模型.md` | `跨端共享需求.md` | `03-架构/跨端共享层.md` |
|---|---|---|---|
| 回答的问题 | **领域里有什么** | **两端怎么写才一致** | **这些契约在工程里怎么组织** |
| 产出条件 | **两档都产出**（含单端开发） | **仅两端都开发时产出** | **仅两端都开发时产出** |
| 承载内容 | 术语表（术语 / 权威名 / 定义）、实体**完整字段表**（语义 / 类型口径 / 可选性 / 取值约束 / 默认值）、不变量（带编号）、**枚举取值语义** | 共享 / 分叉边界、**命名规范**（禁止同义词 / 双端字面映射 / 缩写白名单）、接口规范、《字段**跨端**核对》（线格式 / 双端差异 / 跨端一致性要求）、《枚举**跨端**核对》（线格式 / 双端字面 / 未知值处理 / 冻结或可增长）、口径铁律、错误语义、兼容性 | 模块与包边界、依赖方向、契约的**代码落点**、序列化与持久化实现、可替换 seam、架构级变更同步机制 |
| **不承载** | 跨端字面 / 口径 / 错误对齐 | 字段的语义与类型、不变量条文（只引用编号） | **不复制任何契约条文**——只写「落在哪、怎么实现」 |
| 事实源地位 | 字段的**语义与类型**以它为准 | 凡涉及「两端」的约束以它为准（**跨端契约的事实源**） | 契约的**工程落点**以它为准；内容以阶段 1 两份为准 |
| 冲突处理 | — | 先改跨端档，再**回写**领域模型 | **跟随阶段 1 修改**，不得在架构层把契约"改一遍" |

**判据口诀**：
- 这句话单端也成立吗？→ 是 → 属于 `领域模型.md`；只有两端才有意义 → 属于 `跨端共享需求.md`。
- 「这条契约在代码里落在哪个模块、怎么序列化」→ 属于 `03-架构/跨端共享层.md`。
- 同一个字段名在三份文件里都出现是**正常的**（一份说它是什么，一份说两端怎么写，一份说它落在哪），但**不得重复同一列**。

**典型违规**（写模板时最容易犯）：
- 在跨端档重抄术语的"定义"列 → 应只写"禁止同义词"，定义指向领域模型。
- 在跨端档重抄字段的类型口径 / 可选性 / 默认值 → 应只写线格式、双端字面、跨端差异。
- 在跨端档重抄不变量条文 → 应只**引用编号**（`V1`、`V2`）并声明"两端都须成立"。
- 在领域模型里写"两端字面差异" → 单端场景没有"两端"，该列只能属于跨端档。
- **在 `03-架构/跨端共享层.md` 重抄实体字段表 / 不变量清单 / 数据契约取值** → 架构层只写「契约落点表」（契约来源 § → 两端代码位置 → 谁保证一致），条文一律引用阶段 1 两份文档。

### 2.2 其余收敛型产物的归属

`原型说明.md` / `原型图.html` / `架构审计.md` / `回滚方案.md` / `任务拆分.md` / `测试计划.md` 无跨文件重叠问题，
各有唯一阶段归属，按第 6 节清单产出即可。

## 3. 统一目录规范（批次层 + 阶段分类目录 + 入口导航）

`templates/` 与目标工程的 `docs/<feature>/` **同构**——同样的批次层与阶段子目录、同样的文件命名，
模板目录就是"一份空壳的标准产物目录"（批次层用占位目录名 `<批次>` 表示）。落地时按同样的树往
`docs/<feature>/` 里填：

```
docs/<feature>/                          templates/ 中同构对应
├── 00-入口/                                          ← 全局单例（无批次）
│   └── 文档导航.md              # 批次清单 + 读取顺序 + 冲突优先级 + 分派口径
├── 01-需求/                                          ← 批次内
│   └── <批次>/                  # 如 01-阅读进度续读
│       ├── 需求-00-<短名>.md     # 需求理清（追加型：新版本→新建 01-、02-…）
│       ├── 领域模型.md          # 领域模型（术语表 + 实体完整字段表 + 不变量 + 枚举取值语义）（收敛型）
│       ├── 用户故事-00-<短名>.md # 用户故事（含验收场景）              （追加型）
│       └── 跨端共享需求.md       # 仅两端都要时：跨端契约事实源——命名(含双端字面映射)/接口/字段跨端核对/枚举跨端核对/口径/错误（收敛型）
├── 02-原型/                                          ← 批次内
│   └── <批次>/
│       ├── 原型说明.md          # 页面清单 + 关键交互 + 状态覆盖 + 视觉稿规格 + 设计取舍 + 走查记录
│       └── 原型图.html          # 视觉稿 + 交互原型（单文件零依赖、双击即开）
├── 03-架构/                                          ← 【项目总体架构约束层】全局单例，无批次目录；所有批次共享，别处改动须增量更新
│   ├── 待查证问题.md            # 待查证技术问题清单
│   ├── 事实纪要.md              # 白名单搜索事实纪要（带一手引用）
│   ├── 设计约束.md              # 设计硬约束
│   ├── 候选方案.md              # 多套方案
│   ├── 方案对比.md              # 方案对比
│   ├── 跨端共享层.md            # 共享层（模块边界 · 依赖方向 · 契约落点 · 序列化实现）
│   └── 方案草案.md              # 落地方案草案（架构基线）
├── 04-落地计划/                                      ← 批次内
│   └── <批次>/
│       ├── 架构审计.md          # 既有架构审计                    （收敛型）
│       ├── 变更清单-00-<短名>.md # 变更清单（追加型：每次改动新建一个编号）
│       ├── 回滚方案.md          # 回滚方式                        （收敛型）
│       └── 任务拆分.md          # 任务拆分                        （收敛型）
├── 05-实现与测试/                                    ← 批次内
│   └── <批次>/
│       ├── 测试计划.md          # 测试计划（测试栈 + seam + should 用例）（收敛型）
│       └── (测试代码/源码在各工程目录，不在此处)
├── 06-交付/                                          ← 批次内
│   └── <批次>/
│       ├── 编译报告-00-<短名>.md # 双端编译报告                    （追加型）
│       ├── 审查报告-00-<短名>.md # 审查报告                        （追加型）
│       ├── 一致性对账-00-<短名>.md # 代码↔文档对账（交付门槛，lite 不省略）（追加型）
│       └── 交付报告-00-<短名>.md # 交付报告                        （追加型）
└── 99-来源与日志/                                    ← 全局单例（无批次）
    ├── (原始需求/设计稿等来源材料)
    └── 运行日志.jsonl           # 全程增量日志
```

`<feature>` 用功能短名（如 `订阅管理`），由任务 1.1 定名并初始化目录。
`<批次>` 用 `NN-<需求名>`（如 `01-阅读进度续读`），由任务 1.1 建立并写入批次清单。
`templates/模板说明.md`（本文件）是模板体系的**总则**，不对应功能产物，不参与同构复制。

## 4. 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 阶段目录 | `NN-中文阶段名`，NN 为阶段序号 | `02-原型/<批次>/`、`04-落地计划/<批次>/` |
| **批次目录** | **`NN-需求名`**，NN 两位数字从 `01` 起**连续递增**，需求名为**功能语义中文短名** | `01-阅读进度续读/`、`02-书架批量管理/` |
| 收敛型产物 | `中文类型名.md`（无序号） | `领域模型.md`、`方案草案.md` |
| 追加型产物 | `中文类型-NN-<短名>.md`，NN 两位数字从 `00` 起**连续递增** | `需求-00-阅读进度续读.md`、`需求-01-书架批量管理.md` |
| 每个序号文件的标题 | 该版本/该实例的**功能语义短名**（中文，能一眼看懂做什么） | `需求-01-书架批量管理.md` 而非 `需求-01.md` |

- **短名必须承载功能语义**，是"这次新增的是什么"，不是序号复读或占位符。
- **序号只增不改**：修正历史记录 = 新建下一个编号并说明"取代 需求-01"，而不是回头改旧文件。
- **两处序号都要连续**：批次序号 `01,02,03…`，批次内序号 `00,01,02…`（跳号意味着记录遗失，校验器会提示）。

## 5. 每个模板的通用头部（所有产物文件必含）

每个产物文件头部必须声明「导航入口 + 所属阶段 + **作用域/批次** + **产物类型** + 依赖索引」，
保持产物之间可互链、可追踪。

**批次内产物**：

```markdown
# <产物名>

> 导航入口：`../../00-入口/文档导航.md`。开发/评审先读导航，再进本文件。
> 所属阶段：<阶段名>。任务编号：<X.Y>。
> **所属批次：`<批次>`**（= `NN-<需求名>`，如 `01-阅读进度续读`）。批次目录名在 01/02/04/05/06 各阶段间**必须同名对齐**。
> **产物类型：追加型（批次内）**。命名 `<类型>-NN-<短名>.md`（NN 两位数字，从 00 起递增）。
> **每次新增内容 → 新建下一个编号的文件**，不得在本文件上增删改（这是追加式演进，历史文件保持不可变）。
> 若本文件新增/修改了领域模型、数据契约、测试用例或原型页面，须同步更新对应阶段产物。
```

批次内收敛型把最后两段替换为：

```markdown
> **产物类型：收敛型（批次内）**。命名 `<类型>.md`（无序号单例）。
> 表达「**本批次结束时的**当前真相」，随本轮上游产物演进**原地更新**，不另建版本文件。
> **非首批次开工时，应先从上一批次的同名文件继承**，再在本批次内继续演进。
```

**全局单例产物**：

```markdown
> 导航入口：`../00-入口/文档导航.md`。所属阶段：<阶段名>。任务编号：<X.Y>。
> **作用域：全局单例**（不属任何批次）。架构层为**所有批次共享**，本文件表达全项目当前架构真相。
> **产物类型：收敛型（全局）**。命名 `<类型>.md`（无序号单例）。就地更新。
> 架构改动须**全项目同步**（文档 + 代码 + 所有活跃批次的相关产物），见 `references/代码文档同步.md`。
```

> 作用域与类型声明位置固定——这是模型生成产物时的自检点，也是人工评审的第一眼信息。

## 7. 校验器核验规则

`scan-artifacts.py` 分三层核验：

**第 0 层：批次结构**——
1. **批次发现**：扫出各阶段目录下的批次目录名（如 `01-阅读进度续读`）。
2. **批次对齐**：各阶段（01/02/04/05/06）的批次名集合**必须一致**；某阶段缺了同名批次目录 → 报「批次未对齐」，
   说明这一轮漏跑了那个阶段。
3. **批次序号连续**：批次目录序号须为 `01,02,03…` 无跳号。

**第 1 层：收敛型（单实例）**——两件事：
1. **存在性**：文件是否落在 `docs/<feature>/` 的正确路径（批次内产物须落在对应批次目录下）。
2. **结构核验**：文件内是否包含该模板声明的「必填章节」关键词（第 6 节表格「必填章节」列）。

**第 2 层：追加型（多实例）**——三条规则：
1. **至少一个**：`<类型>-*.md` 至少匹配到一个文件，否则判「缺失」。
2. **逐个过关**：每个匹配文件都要通过必填章节核验，任一不过则整体判「缺字段」并列出问题文件。
3. **序号连续**：批次内序号须为 `00,01,02…` 无跳号，跳号在报告中提示。

四态判定：

| 状态 | 含义 |
|---|---|
| ✅ 已产出 | 文件存在 + 必填章节命中（追加型则全部匹配文件都命中） |
| ⚠️ 缺字段 | 文件存在，但部分必填章节缺失（列出缺哪些；追加型会列出问题文件） |
| ⭕ 不判定 | 产物落在各工程目录（测试代码/源码），脚本无法从 docs/ 判定 |
| ❌ 缺失 | 文件不存在（追加型表现为该类型无任何匹配文件） |

报告**按批次分组**呈现，并单列「全局单例」区。

> 说明：移动端场景下，阶段 5 的测试代码与源码落在各工程目录而非 docs/，校验器对这类任务标
> 「不判定」，由阶段 6.1 双端编译门兜底。
>
> **同一产物被多个任务核验**：`02-原型/<批次>/原型说明.md` 由任务 2.1（页面清单/关键交互/状态覆盖）
> 与 2.3（视觉稿规格/设计取舍/走查记录）分别核验不同章节，二者都过才算原型层完整。

## 8. 功能分级（tier）与模板裁剪

`iherefor-smart-development` 按需求规模分两档，判据与闸门收缩见 `config/tier.json`。两档**共用同一套模板目录**，
不另造「lite 专用模板」——lite 档只是把部分产物标为可跳过，避免模板体系翻倍：

| 档位 | 闸门 | 模板全集 |
|---|---|---|
| **full**（标准） | a / **p** / b / c1 / c2 / d / 交付门 | 上表 23 个产物模板全套 |
| **lite**（轻量） | a / **p** / b / d / 交付门 | 跳过 6 个（**全是批次内收敛型**）：`01-需求/<批次>/跨端共享需求.md`、`03-架构/候选方案.md`、`03-架构/方案对比.md`、`03-架构/跨端共享层.md`、`04-落地计划/<批次>/架构审计.md`、`04-落地计划/<批次>/任务拆分.md` |

- **原型层不因档位省略**：`02-原型/<批次>/原型说明.md` 与 `原型图.html` 两档都要产出（界面决策属"约束"不属"仪式"），
  lite 档只收缩为**单变体 + 单平台**。
- **追加型产物不因档位省编号**：lite 档同样按 `类型-NN-<短名>.md` 新建，只是实例通常会少。
- **批次对齐不因档位放松**：lite 档同样要在 5 个阶段建同名批次目录，只是批次内产物更少。
- lite 档 `03-架构/方案草案.md` 需在模板内**同载「变更清单 + 执行步骤」**（替代独立的变更清单审批与任务拆分）。
- `scan-artifacts.py --tier lite` 对上述 6 个跳过产物标「已跳过」（用 glob 匹配路径），不判缺失。
- 判据、可升降级规则、跳过清单的**唯一数据源**是 `config/tier.json`，本文档不另行复制判据。
