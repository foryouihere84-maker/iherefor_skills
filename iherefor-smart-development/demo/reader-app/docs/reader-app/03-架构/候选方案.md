## 方案 1 — Readium 全家桶（重依赖、最省心）

以 Readium 作为双端电子书解析与阅读的统一引擎（iOS 用 Swift Toolkit，Android 用 Kotlin Toolkit），业务层只做「书架 + 调用 Readium」。

- **接口/模块设计**：`LibraryRepository`（书架 CRUD）→ `BookParser`（薄封装，内部调 Readium R2Streamer）→ `ReaderScreen`（直接嵌入 Readium 阅读器视图）。EPUB/PDF/TXT 全部交给 Readium 处理。
- **depth（深度）**：浅封装，业务逻辑少，大量能力外包给 Readium。
- **locality（局部性）**：优点——格式解析复杂度全部收敛到 Readium 一处；缺点——Readium 是巨依赖，核心逻辑不可见、难定制。
- **seam 位置**：`BookParser` 接口是唯一可测 seam；Readium 内部不可测。

## 方案 2 — 自研解析 + 系统 PDF（零第三方、最可控）

不引入任何第三方解析库：EPUB 自研（解 ZIP + 解析 OPF/NCX + 抽章节纯文本），TXT 自研切分，PDF 用系统内置 PDFKit/PdfRenderer。解析逻辑放共享层纯函数，两端复用同一套领域规则。

- **接口/模块设计**：`BookFormatDetector`（格式识别）→ `EpubParser` / `TxtParser`（协议 `BookParser` 实现）→ `ParsedBook`（文档流/章节）→ `ReaderViewModel`。PDF 走独立的 `PdfReader`（系统渲染）。
- **depth（深度）**：深——EPUB 解析自研，复杂度落在自家代码里；但换来完全可控、可测。
- **locality（局部性）**：领域解析规则集中在共享层，两端只做平台渲染差异；PDF 渲染局部性差（两端各用系统 API，逻辑必然分叉）。
- **seam 位置**：`BookParser` 协议 + 各个 parser 的纯函数层，seam 充分、可测性最好。

## 方案 3 — 混合：TXT/EPUB 共享纯函数 + 系统 PDF + 预留 Readium 升级点

以方案 2 的「自研 + 系统 PDF」为骨架，但不把 EPUB 解析写死：抽象 `BookParser` 协议，TXT 用纯函数实现、EPUB 首版用自研最小解析器，但协议设计时预留 Readium 替换位（接口与 Readium 的 Publication 语义对齐），未来可一键切换到 Readium 深度解析（书架/目录/样式）。

- **接口/模块设计**：`BookParser` 协议 + `ParsedBook`/`Chapter`/`ReadingProgress` 作为跨端共享契约（与 Readium Locator 语义对齐）→ `TxtParser`（纯函数）/ `EpubParser`（自研最小）实现 → Reader 层按 `BookFormat` 分派渲染。
- **depth（深度）**：中——自研 EPUB 但协议对齐 Readium，深度与灵活性折中。
- **locality（局部性）**：解析规则集中共享层；PDF 渲染分叉不可避免；协议抽象预留了未来把 EPUB 解析局部性外迁到 Readium 的反转点。
- **seam 位置**：`BookParser` 协议是可替换 seam（解析引擎可插拔），领域纯函数层可测。

## 方案 4 — 最简 MVP：只读纯文本流（不推荐，仅作对比下限）

不区分格式做结构化解析，所有格式统一「解出纯文本流」后按行渲染。PDF 也抽文本（丢失版式）。实现最快但体验极差、违背「按格式阅读」的需求与不变量（PDF 需按页、进度定位与格式兼容）。列入仅作对比下限。

- **depth / locality / seam**：最浅；所有格式塌缩成纯文本；seam 虽简单但语义错误。
