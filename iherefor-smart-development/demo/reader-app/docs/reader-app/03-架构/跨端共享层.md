## 1. 共享层边界与组成

### 1.1 模块与包结构

两端**同构分层**：`Domain`（纯领域）/ `Data`（仓库与视图模型）/ `Parsing`（解析）/ UI。共享契约落在前三层。

| 端 | 共享层所在位置 | 包含的模块 / 类型 | 说明 |
|---|---|---|---|
| iOS | `ios/ReaderApp/` | `Domain/`：`Book.swift`（`Book` / `ReadingProgress` / `BookFormat` / `LocatorType`）、`SharedRules.swift`（不变量纯函数）<br>`Data/`：`LibraryRepository.swift`（协议 + `InMemoryLibraryRepository`）、`LibraryViewModel.swift`<br>`Parsing/`：`BookParser.swift`（协议）、`BookReaderService.swift`、`EpubParser.swift` / `TxtParser.swift` / `MiniZip.swift` | UI 在 `LibraryView.swift` / `Reader/ReaderView.swift`，不属共享层 |
| Android | `android/app/src/main/java/com/iherefor/readerapp/` | `domain/`：`Book.kt`（同 4 个类型）、`SharedRules.kt`<br>`data/`：`LibraryRepository.kt`（接口 + `InMemoryLibraryRepository`）、`LibraryViewModel.kt`<br>`parsing/`：`BookParser.kt`、`BookReaderService.kt`、`EpubParser.kt` / `TxtParser.kt` / `MiniZip.kt` | UI 在 `MainActivity.kt` / `reader/ReaderScreen.kt`，不属共享层 |

### 1.2 依赖方向

```
UI (LibraryView / ReaderView · MainActivity / ReaderScreen)
        ↓ 只向下
Data (LibraryRepository · LibraryViewModel)
        ↓
Domain (Book · SharedRules)          Parsing (BookReaderService · Epub/TxtParser)
        ↓                                   ↓ 只向下
平台能力 (文件访问 · PDFKit / PdfRenderer · Compression / ZipInputStream)
```

| 模块 | 允许依赖 | 禁止依赖 | 理由 |
|---|---|---|---|
| `Domain` | 仅标准库 | `Data` / `Parsing` / UI / 平台能力 | 领域类型与不变量纯函数必须可独立测试，且两端行为等价 |
| `Parsing` | `Domain` + 平台能力 | `Data` / UI | 解析只把字节变成领域对象，不写仓库 |
| `Data` | `Domain` | UI / 平台能力中的 UI 部分 | 仓库是 seam，视图模型不直接碰平台 API |
| UI | `Data` / `Domain` / `Parsing` | — | UI 是唯一可自由依赖的平台相关层 |

> **禁止的反向依赖**：`Domain` 不得 import `Data` / 平台框架（Swift 侧表现为不 import `SwiftUI`/`PDFKit`；
> Kotlin 侧不 import `android.*`）。这是两端能共用同一份不变量语义的结构前提。

### 1.3 落地层引用方式

**首版无跨语言代码生成**：两端各自维护同构的 `Domain` 包，命名与字段由 `01-需求` 两份文档约束，
一致性靠「第 2 节的落点表 + 阶段 6 一致性对账」保证。

| 机制 | 本项目做法 | 代价 / 风险 |
|---|---|---|
| 契约传递 | 人工按文档实现，**无代码生成** | 字面漂移无编译期拦截——**已实测发生**：见 `跨端共享需求.md` 2.3 D1 / 7.1 E5、E6 |
| 防各自独立建模 | `Domain` 层只允许纯领域类型；两端字段名/方法名以 `跨端共享需求.md` 为唯一裁决 | 需要交付门「一致性对账」兜底 |
| 后续演进候选 | 若漂移反复出现，可引入 schema 生成（如从线格式定义生成两端类型） | 属第 5 节 S4 类变更 |

## 3. 序列化与持久化实现

| 项 | 方案 | 与线格式列的对应 | 备注 |
|---|---|---|---|
| 序列化格式 / 库 | 首版**无落盘**；目标 JSON（iOS `Codable` / Kotlin 可序列化类） | 见 `跨端共享需求.md` 第 4.2 节 | `Chapter` / `ParsedBook` 仅内存，不参与序列化 |
| 字段名映射机制 | camelCase 直通（线格式名 = 代码属性名） | 唯一例外：`id` 需两端统一 **lowercase** | 见 `跨端共享需求.md` 2.3 D1 |
| 时间表示 | epoch 毫秒（64 位整型）；iOS `Date` ↔ Kotlin `Long` | 第 6 节「时间点」 | `importedAt` / `updatedAt` |
| 持久化介质 | **内存**（`InMemoryLibraryRepository`），随进程退出丢失 | — | 属 `跨端共享需求.md` 第 8 节 C6「持久化落地」待办 |

| 未知字段 / 未知枚举处理机制 | **当前两端均未实现**；目标：未知字段忽略、未知枚举降级为未知值 | 第 4.2 节与 5.1「未知值处理」 | **E2 待收敛**：当前枚举遇未知值直接解码失败 |

## 4. 可替换 seam 与测试策略

| seam | 作用 | iOS 实现 | Android 实现 | 测试替身 | 共享契约测试落点 |

| `BookParser` | 按格式解析为章节流 | `EpubParser` / `TxtParser`（协议 `BookParser`） | `EpubParser` / `TxtParser`（接口 `BookParser`） | 假 parser 注入 `BookReaderService` | `ParserTests.swift` / `ParserTest.kt` |
| 文件读取（`readAndParse` 内） | 隔离平台文件 API | 直调 `Data(contentsOf:)` —— **未抽出 seam** | 直调 `contentResolver.openInputStream` —— **未抽出 seam** | 无 | 当前仅端到端手测；**改进点**：抽出 `FileReading` 协议以便断言 E6 行为 |

## 5. 变更同步机制

架构层为全局共享，改动会波及其他**批次**。本节规定「改什么、同步什么、卡在哪」。

| 编号 | 变更类型 | 必须同步的内容 | 卡点 |
|---|---|---|---|
| S1 | 共享层模块边界的划分 / 层次关系变更 | 本文件 + 两端代码 + **所有活跃批次**的落地计划 | 交付门 |
| S2 | 契约本身变更（字段 / 枚举 / 口径 / 错误） | **先改 `01-需求` 两份**，再改本文件第 2 节落点 + 两端代码 | 契约先改 |
| S3 | 序列化 / 持久化方案变更（如 C6 落盘） | 本文件第 3 节 + 两端代码 + 迁移方案 + `一致性对账` | **待办**：C6 落地时触发 |
| S4 | 新增 seam（如抽出 `FileReading` / 时钟） | 本文件第 4 节 + 两端实现 + 测试替身 | 建议在补 E6 断言时一并做 |
