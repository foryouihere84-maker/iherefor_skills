# UI Style Governance（跨平台方法论）

## 目标
让 UI 代码具备以下特性：
- 可维护：风格改动集中、影响可控
- 可扩展：新增页面/组件时尽量复用已有规范
- 可迁移：同一套风格语义可映射到 iOS/Web/Android 等不同平台

---

## 核心原则（平台无关）

1. **单一风格源（Single Source of Truth）**  
   所有视觉与交互风格定义都应来自统一 style 体系，而不是散落在页面/视图实现里。

2. **语义命名优先**  
   用“语义角色”命名（如 `primary-text`, `surface-bg`, `interactive-focus`），不要用实现细节命名（如 `blue-500`, `font16bold`）。

3. **分层治理**  
   - Primitive：原子值（基础色值、尺寸、时长等）
   - Semantic：语义角色（文本主色、危险态背景等）
   - Pattern：组件/页面级样式规则
   - Interaction/Motion：状态与动画规范
   - Adapter：平台映射层（可选）

4. **先复用后新增**  
   新需求先查已有 common 与 domain 规则。仅在无法复用时新增。

5. **全局变更需可解释**  
   修改 common 等全局规则时，必须说明影响范围与回归关注点。

---

## 建议结构（逻辑结构，不绑定具体技术栈）

> 如果项目已有等价结构，可按同样语义映射；不要为了形式强行重构。

- `style/`
  - `common/`
    - `primitives/`（原子变量）
    - `semantics/`（语义映射）
    - `motion/`（动效曲线/时长分级）
    - `interaction/`（hover/pressed/focused/disabled 等状态规范）
  - `domains/`
    - `xxx-style/`（某业务域或页面域风格规则）
  - `adapters/`（可选）
    - `ios/`, `web/`, `android/`（平台映射，不改变语义层）

> `xxx-style` 中的 `xxx` 优先按业务域命名，其次按组件域命名。

---

## 执行流程（每次 UI 任务都走）

1. 识别任务所属域（domain）
2. 查找 `style/domains/<domain>-style` 是否存在
   - 存在：优先复用并增量更新
   - 不存在：新建并给出命名理由
3. 查找 `style/common` 中是否已有可复用语义 token / 动效规范
4. 仅在无法复用时新增 common 项，并记录新增原因
5. 为该任务补齐状态矩阵（如 normal/active/disabled/error/loading）
6. 动效必须引用 common/motion 规范，不允许页面私自定义一套
7. 输出变更报告（见“输出模板”）

---

## 硬约束（必须满足）

- 不在页面/视图实现中直接硬编码视觉值（颜色、字号、间距、圆角、时长等）
- 不重复定义已有语义 token
- 新增样式必须归档到对应 `xxx-style`
- 修改 common 时必须附“影响范围说明”

---

## 通用抽取规则（何时沉淀到 common）

满足任一条件即可抽取到 common：
- 被 2 个及以上 domain/组件复用
- 明显属于品牌一致性规则（主色、标题层级、交互反馈）
- 未来高概率复用（例如通用卡片、按钮、表单状态）
- 影响全局体验统一性（如动效速度、焦点态）

---

## 平台映射原则（iOS / Web / Android 等）

- 语义层保持一致：`primary-text` 在所有平台语义一致
- 实现层可不同：不同平台可用不同语法/机制承载
- 不允许“同语义多风格漂移”：同一语义在不同模块出现视觉偏差时，应回归 common 修正

## 反模式（发现即修正）

- 直接在页面里写临时颜色/尺寸/动画常量
- 用“实现词汇”代替语义命名
- 每个新页面都新建一套近似样式，不复用 common
- 修改全局风格却不说明影响范围

---

## 快速判定：什么时候一定要用本技能？

只要任务涉及以下任意一项，就启用本技能：
- UI 视觉呈现
- 交互状态/反馈
- 动画与过渡
- 主题/品牌一致性
- 样式重构与页面扩展
