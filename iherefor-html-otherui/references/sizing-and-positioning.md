# 尺寸与定位规范（强制）

> 本文是「设计稿 → 原生代码」在**尺寸**与**位置**两条轴上的权威规范。
> 与 [artifact-contract.md](artifact-contract.md#布局关系与控件尺寸的约束口径强制) 的布局比例条款配套阅读：
> 那条约束规定的是**关系**怎么表达，本文规定的是**尺寸**与**位置基准**各自归谁管。

## 0. 一句话

约束策略**不是「把设计稿整页等比缩放」**，也不是「所有尺寸都固定」，而是两条互相独立的轴：

| 轴 | 谁决定 | 表现形式 | 是否随屏幕/容器变化 |
|---|---|---|---|
| **尺寸** | **由闭合方式决定**（设计常量 / 内容固有 / 父约束 / 边界 / 比例） | `fixed` / `intrinsic` / `bounded` / `pinned` / `proportional` / `equal` / `aspect-ratio` | 取决于闭合方式：`fixed` 不变，其余按各自定义求解 |
| **位置** | 父子视图层级关系 | 相对**直接父视图**的约束 | 随父视图求解，不随屏幕比例缩放 |

**设计稿尺寸是参考事实，运行时尺寸由约束闭合。** 两个错误方向要同时挡住：

1. **把整页当成一张图去缩放** —— 等于把「设计稿恰好是 393pt 宽」这个偶然事实提升成了布局规则，
   每个尺寸都被乘了一个屏幕相关的系数。
2. **把每个尺寸都写死** —— 等于把「设计稿在这台设备上量到的值」当成通用答案，
   换宽度档、换字号、换语言就全部失守。

判据是**「这个值由谁闭合」**，不是「这个值等于设计稿的几」。

## 1. 为什么不采用等比缩放：四条理由

1. **字号与最小点击区会被缩放破坏。** 44pt 的点击区在窄屏上缩成 40pt，违反平台规范，也让
   可访问性检查失败。字号缩放则直接破坏排版（换行点、行高、字重光学尺寸都会变）。
2. **设备之间本来就不等比。** `393×852 → 402×874` 两轴比例分别是 `1.0229` 与 `1.0258`，
   根本不是同一个数。「等比」在这里不是一种可选策略，而是一个不存在的东西 —— 真按等比做，
   必须**额外**声明退化成 `fit + letterbox` 还是两轴不等比拉伸，两种都要单独解释、
   并且会引入 letterbox 厚度的系统性偏移。
3. **缩放会沿容器树累积。** 嵌套容器各自按比例缩放时，外层的一次 `multiplier` 会与内层的
   再相乘；误差在最深处最大，而每一层单看都「有出处」。
4. **它掩盖层级错误。** 相对整页（root）的比例在**单页单设备**上永远算得出来，于是组件挂错父视图、
   溢出轨道的负坐标（实测样本里存在 `x = -2` 的元素）也能被一条比例「对齐」过去 ——
   报绿，但约束是错的。

## 2. 闭合方式的八类（两轴），判据是「这个值由谁闭合」

**尺寸一律不写成「相对整页（root）的比例」。** 八类的表达方式：

| 类别 | `kind` | 判据 | 正确表达 | 例 |
|---|---|---|---|---|
| **固定尺寸** | `fixed` | 设计稿给出封闭值，且**有明确的固定视觉语义** | 字面设计值（pt/dp）+ `why` | 图标 24×24、装饰条高 4、头像 48×48、描边 1、圆角 12 |
| **内容固有** | `intrinsic` | 由文字/图标/图片自身决定，**不给宽高约束** | 依赖 `intrinsicContentSize` / `wrap_content` + 必须给 `why` | 文本行高、多行文本高度、自适应标签、按钮内容区 |
| **边界约束** | `bounded` | 内容可变但不能无限扩张 | `>=` / `<=` 常量（至少给 `min` 或 `max` 之一） | 内容列 `maxWidth = 640`、按钮 `height >= 44` |
| **贴父派生** | `pinned` | 值由与父视图的约束闭合 | 约束（等值锚点 + 固定边距），**不带比例系数** | 全宽 CTA（左右各 16）、hero 背景（四边贴 0）、分割线（左右贴 0、高 1） |
| **比例** | `proportional` | **确属**随父容器成比例变化 | `multiplier` + 必须给理由 | 装饰区高度 = 父容器高度 × 0.155 |
| **兄弟相等** | `equal` | 由兄弟元素决定 | `constraintEqualToAnchor` + 必须给 `with`/`to` | 两个卡片等宽、按钮等高、基线对齐 |
| **中心/基线对齐** | `centered` | 相对父或兄弟的锚点对齐 | `centerX` / `centerY` / `baseline` 相等 | 标题居中、图标与文字基线对齐 |
| **比例约束** | `aspect-ratio` | 由自身宽高比决定 | `widthAnchor = heightAnchor × ratio` + 正数 `ratio` | 图片、媒体卡片、视频封面 |

**`fixed` 不是默认值。** 只有当「这个尺寸的固定性本身就是设计意图」时才用它：图标、装饰、边框、
明确固定高度的视觉控件。文本、按钮、容器和内容区域**默认优先 `intrinsic` 或 `bounded`**。

> **为什么 `fixed` 必须降级为特例**：`bounds.width = 220` 是「设计稿在 393pt 宽下量到的 220」，
> 不是「这个元素永远该是 220」。把前者当后者，在窄屏（iPhone SE 375pt、Slide Over 320pt）、
> 动态字体、长本地化文本（德语/俄语往往长 30%+）、iPad 分屏下都会失守。
> 而 `label.leading/trailing` 贴父 + `intrinsic` 高度，在所有这些情形下都成立。

### 2.0 一条关系只声明一个 `kind`

一条关系描述的是一件事：**这个量由谁闭合**。所以每条关系只有一个 `kind`，
**没有**内嵌的 `relations` 子数组 —— 写进去不会有任何代码读它（`bounded` 分支不看
`edges`/`insets`），校验器也**不会报错**，只会**静默丢掉**：产物照样判 `pass`，
而你以为已经声明过的内边距根本不在里面。这是本契约里最贵的一种错法，因为它没有症状。

```json
{"id": "SubscriptionCard.width", "axis": "width", "of": "page",
 "kind": "pinned", "edges": ["leading", "trailing"],
 "insets": {"leading": 16, "trailing": 16},
 "why": "宽度由两侧各 16pt 内边距闭合"}
```

```json
{"id": "SubscriptionCard.height", "axis": "height", "of": "page",
 "kind": "intrinsic", "minimum": 68,
 "why": "标题、价格和辅助文案支持动态字体及多语言换行，高度由内容撑开"}
```

```json
{"id": "HeroImage.height", "axis": "height", "of": "page",
 "kind": "aspect-ratio", "ratio": 1.7778,
 "why": "位图资源自身决定比例，宽度贴父后高度随之求解"}
```

读法：卡片宽由「贴父两侧 + 16pt 内边距」闭合；卡片高由内容撑开、68 只是下限；
Hero 图高由 16:9 比例闭合。**`fixed` 没有出现在任何一条里 —— 这是正常的。**

「不能再宽下去」的**上限**不是闭合方式，它属于宽度轴，写在
`adaptiveLayout.regions[].maxContentWidth` 里（`widthPolicy` 取 `max-content-width`
或 `centered-column` 时必需）。**别把它塞进同一条关系**：

```json
{"region": "SubscriptionCard", "widthPolicy": "max-content-width",
 "maxContentWidth": {"value": 600, "of": "root", "reason": "平板下不被拉成超宽条"}}
```

### 2.0.1 类别选择速查

| 这个量是什么 | 默认 `kind` |
|---|---|
| 图标、头像、装饰、边框、分隔线粗细 | `fixed` |
| 文本、标签、按钮内容、可变文案容器 | `intrinsic` |
| 按钮高度下限、内容列宽度上限、卡片最大宽 | `bounded` |
| 贴父边缘的边距、铺满、等分 | `pinned` |
| 图片、视频、媒体封面 | `aspect-ratio` |
| 多个兄弟要一样宽/一样高 | `equal` |
| 居中、与兄弟对齐 | `centered` |
| 确实随父容器成比例（背景装饰、进度条填充） | `proportional` |

### 2.1 「贴父」不等于「比例」（最容易踩的偏差）

设计稿说「左右各留 16pt」，正确的实现是 `leading = parent.leading + 16` 与
`trailing = parent.trailing - 16`：**这条关系已经闭合，16 是设计常量，不是父容器宽度的函数。**

若改写成 `width = parent.width * 0.9186`（因为 `(393-32)/393`），在 430pt 宽的设备上会得到
**13.7pt 的边距** —— 设计稿说的是 16pt。两个数在探针设备上都「对得上」，只有换设备才分岔。

> 判据：**这个数值是设计稿直接给的常量，还是只在这台设备上等于设计稿给的常量？**
> 前者是 `fixed`（若有固定语义）或 `pinned` 的边距（若是间距），后者要么是 `pinned`（约束闭合），
> 要么是 `proportional`（确实成比例）。

### 2.2 哪些量确实该用 `fixed`（也就是「永远不缩放」的那一小组）

这一节是 §2 的**具体化**：`fixed` 不是默认值，但有一小组量确实天生该固定 —— 它们是
**视觉常量**，其固定性本身就是设计意图，且在多宽度档下必须逐字相同：

字号、行高、圆角、描边宽度、阴影、最小点击区（≥44pt / 48dp）、图标与位图资源的**点值尺寸**、
以及所有标准间距（4 / 8 / 12 / 16 / 24 / 32）、边框与分隔线粗细。这些在**同一平台的不同屏幕 / 宽度档之间**取同一个设计值。

**注意范围**：这一组管的是**视觉常量**，不包括「按钮宽度」「卡片高度」「文字区宽度」这类
**尺寸量** —— 后者即使设计稿给了明确数值，也应按 §2 的判据选择 `intrinsic` / `bounded` / `pinned`。
把它们一起塞进 `fixed`，正是旧契约最致命的地方。

**本条管的是「实现侧写什么」，不是「像素 diff 能不能到 0」。** 这两件事必须分开，
否则会推出一个自相矛盾的期待：既然字号不缩放，基准图与实机图的字形就该逐像素重合。
事实上不会，而且**永远不会** —— 原因在测量侧：基准图是在 `scale(1.0229)` 的画布上渲染的，
所以 **基准字形 = 设计字号 × 1.0229**；实现侧按本条取设计字号，两者天然差 2.29%。
这个差足以让字形边缘的相位差越过强边配对容差（`--edge-tolerance` 默认 2px），
被比较器归入 `structuralRatio`。

于是两条对称的纪律：

- **不许**缩放字号 —— 那会破坏排版、命中可访问性红线，见 §6 反例清单末行。
- **应当**把「字号不缩放」作为硬约束写进实现计划，不因任何测量产物而松动。

**多设备稿的「照稿还原」（不是例外，是另一种输入形态）：** 当同一设计在 Lanhu 里同时有
`xx` 与 `xx-iPad` 两份稿时，这两份稿是**两套并列的独立参考**，iPad 组件的宽、高、
**字号**、圆角、描边全部以 `xx-iPad` 稿自身为准，与 `xx` 稿**没有派生关系**。
「把手机稿等比放大到 iPad」这个说法不成立——「放大」需要「从手机稿派生」这个前提，
而双稿之间不存在这个前提。照 `xx-iPad` 稿还原不是「擅自缩放」，是「取了一个独立的参考值」。
跨平台的尺寸 / 字号若照两份稿各自取值、出现了差异，必须逐档声明在
`adaptiveLayout.sizeVariants[]`，规则见 [adaptive-layout.md §4.1](adaptive-layout.md#41-宽度轴改变容器闭合结果不缩放视觉常量)。
**关键界线**：iPhone 与 iPad 的字号、圆角、描边、最小点击区**可以相同，也可以不同**，二者没有强关联——
它们各自从自己的稿里取值。唯一不随稿动的是**平台硬下限**（最小点击区 ≥44pt / 48dp），
那是可访问性规范，不是设计值。

> 一句话：**§2.2 保证的是「实现不引入缩放」，不是「diff 恒等于 0」。**
> 前者是义务，后者是对基准画布的误解。把后者当前者，就会开始改字号去凑闸门。

这个下界**只对文字类结构差异成立**。`fillRatio` 超限、或结构差异超出声明下界，仍然判 `fail`
—— 下界是「不可消除的下界」，不是「豁免额度」。

### 2.3 动态字体：不再是「例外」，而是 `intrinsic` 的正常结果

旧契约把动态字体当作「唯一需要给固定尺寸开口子的地方」——这个说法本身就暴露了旧契约的问题：
**一个需要开例外的总原则，说明它站不住。**

新契约下这一条不需要例外机制。文本类尺寸默认就是 `intrinsic`：

- 字号仍取**设计值**（走 `UIFontMetrics` / `scaledFont` 之类的缩放通道，而非布局缩放）；
- 承载文字的容器宽度由 `pinned` / `bounded` 闭合，高度由内容撑开；
- 按钮用 `bounded`（`height >= 44`）表达触控下限，**不写死 44**，允许大字号下增高；
- **不允许**反过来缩小字号去迁就固定高度。

也就是说：动态字体成立不需要任何豁免 —— 只要在计划里**没有**把文本容器写成 `fixed` 就行。
计划的 `layoutProportions` 里若某个文本区域的尺寸 `kind` 是 `fixed`，它就是一个**待解释的疑点**，
必须在 `why` 里说清为什么这个文本不会随字号变化（例如它是单字图片化的 Logo 文字）。
说不清的一律改判为 `intrinsic` / `bounded`。

## 3. 位置轴：相对直接父视图，而不是相对 root

每条位置关系都必须写明**基准是谁**。省略基准、一律用 `self.view`（或 `root`），是定位错误的头号来源。

### 3.1 基准规则

1. **默认基准是直接父视图**，不是页面根。关系里必须带 `of`，取值是该父视图的身份
   （`"root"` 仅当该元素的直接父视图就是整屏画布时）。
2. **父容器为整块屏幕画布时**，`of = "root"`，位置参照该父容器（即屏幕内容区，并扣除安全区）。
   这是最常见的一档，也是**唯一**可以写 `of: "root"` 的档位。
3. **嵌套情形同理递推**：卡片里的按钮参照卡片，卡片参照屏幕；工具条里的图标参照工具条。
   一条关系只允许有一个基准，不允许「左边缘参照父、右边缘参照祖父」这种混合写法。
4. **基准由权威来源自动推导**：主链路 `dds-schema.json` 的每个节点带 `parent_id`（根节点的
   直接父即整屏画布），备用链路 `page-facts.json` 的每个元素带 `parentIndex`
   （根元素的直接父即整屏画布，为 `null`）与 `parentHops`，所以「`of` 是哪个父视图」
   是可算的，不必猜。权威来源里判不出层级的元素，实现计划里必须写成待确认项，
   而不是默认填 `root`。

#### 3.1.1 第一层子视图：横向可重排，纵向由内容链闭合

当设备尺寸与 Lanhu 设计稿尺寸**不一致**时，光靠「贴边/居中」是不足以自适应的——它们只保证
与父边的**间距**不变，不会让整页内容随新的宽高重新分布。所以「直接父视图 = 页面（page）」的
**第一层子视图**有一套区别于嵌套层的规则：

| 轴 | 第一层子视图（直接父 = page） | 第二层及更深（父 = 某个容器） |
|---|---|---|
| **水平位置** | **按页面宽度比例**（`x = page.width × ratio`） | 相对直接父视图**固定**（贴边/居中） |
| **垂直位置** | top/bottom、垂直栈、滚动内容链；仅明确的画布装饰使用比例 | 相对直接父视图约束 |
| **尺寸** | 按 §2 的判据闭合（`intrinsic` / `bounded` / `pinned` 优先；只有视觉常量才 `fixed`） | 同上，判据相同 |

三条结论（缺一不可）：

1. **「按比例」只作用于明确声明的关系，不作用于尺寸。** 第一层子视图的水平位置可以重排，
   但它的**尺寸**仍由 §2 的闭合方式决定 —— 位置的比例化不会、也不得把尺寸一起比例化。
   把第一层尺寸也比例化，就等于回到「整页等比缩放」，字号/圆角/最小点击区会一起被破坏。
   **同时，也不能走到另一个极端把第一层尺寸一律写死**：容器、文本、按钮在第一层同样优先
   `intrinsic` / `bounded` / `pinned`，只有图标、装饰等视觉常量用 `fixed`。
   第一层最容易出现的错误是「位置对、尺寸死」——位置会跟着换设备动，尺寸不会，
   于是窄屏上出现挤压或溢出。
2. **纵向优先形成连续内容链**：从 safe-area 顶部到内容底部，每个区域由 top/bottom、spacing、
   intrinsic height 或 bounded height 闭合。内容超过窗口时使用 UIScrollView，不压缩整列间距或字号。
3. **只有第一层横向可按页面比例**：第一层 → 第二层的**相对关系必须固定**（第二层的位置基准是它的
   直接父视图，即某个第一层元素，不是页面）。若把嵌套层也按页面比例排，父容器尺寸一变，
   内部布局会整体漂移。
4. **横向按比例写的是约束，不是绝对值**：实现侧写 `multiplier`（相对 page 的比例原语），
   **不得**写成「探针设备上的绝对坐标」（如 `x = 83`、`y = 132`）。后者只在探针设备上对，换台设备就错
   ——这正是 `forbiddenLiterals` 对第一层同样要拦的原因。

判定「第一层」的依据是事实表：`parentIndex == page 外框的 index`（即直接父视图就是页面）。
生成端只对这些元素的水平位置标记 `forced: "first-level"`；纵向仍按普通约束分类。

#### 3.1.2 水平轴受宽度档收口，垂直轴使用 Auto Layout 内容链

**「水平位置按页面比例」不是一条通用规则，它只在小宽度差下成立。** 垂直轴不沿用这条规则：

- **水平位置** `x = page.width × ratio` 受**宽度档**收口。它在 `393×852 → 402×874` 上是对的
  （两轴比例分别 1.0229 与 1.0258，位置跟着动 2.3%），但推到平板宽度（1024pt）就会出事 ——
  位置按比例 ×2.6、而尺寸按 §2 的契约基本不变（`bounded` / `intrinsic` 的上下界是设计常量，不随窗口缩放）：

  | 元素 | 手机 393pt | 按位置比例推到 1024pt | 结果 |
  |---|---|---|---|
  | 卡片左起 | 33pt | 86pt（33 × 2.604） | — |
  | 卡片宽度 | 327pt（`bounded`，max 与手机宽相当） | **仍被封在 max 内** | 右侧空出大片空白 |
  | 卡片间距 | 13pt（设计常量） | **285pt** | 视觉关系断裂 |

  **注意**：这里的结论不是「卡片宽度该按比例放大到 851pt」——那会得到一张荒谬的巨卡。
  正确的收口是 `widthPolicy`（`max-content-width` / `centered-column`），
  把内容收进一个居中的、有上限的列里。**尺寸的边界是不随窗口缩放的常量，位置与容器宽度才是响应式的。**
  这正是「位置按比例 + 尺寸按闭合」两条规则必须分开的原因。

  所以计划声明了 `adaptiveLayout`（宽度轴，见 [adaptive-layout.md](adaptive-layout.md)）时，
  **水平位置**只在 `compact` 档按页面比例；regular / medium / expanded 档下改由
  `widthPolicy` 重排（`max-content-width` 就是把它们收进居中的内容列里）。
  这条收口由 `adaptiveLayout.firstLevelWidthClass` 表达（缺省 `compact`），
  由 `scripts/check_adaptive_layout.py` 核对 —— 它**只管水平轴**。

- **垂直位置**由 safe area、相邻元素、UIStackView spacing、intrinsic height 和滚动内容链闭合。
  短屏、横屏、Dynamic Type 或长文本下，内容允许增高并滚动；不能通过整体压缩间距、字号或
  `page.height × ratio` 把整列强行塞进窗口。只有装饰、媒体裁剪区等确有画布比例语义的元素才使用
  `proportional`，并写 `why`。

### 3.2 位置关系的四种表达（按优先级）

| 优先 | 形式 | 何时用 | 例 |
|---|---|---|---|
| 1 | 贴父边 + 固定间距 | 元素与父边有关系 | `top = parent.top + 24`、`leading = parent.leading + 16` |
| 2 | 居中/对齐锚点 | 元素相对父视图居中或"与某兄弟对齐" | `centerX = parent.centerX`、`top = sibling.bottom + 8` |
| 3 | 比例 | 关系**确实**随父容器尺寸成比例变化，且必须显式给理由 | 背景装饰高度 = 父容器高度 × 0.155 |
| 4 | 绝对坐标字面量 | **禁止** | `frame.origin.x = 83` |

比例是第 3 优先，不是默认项；而且一旦使用，**基准必须是父视图**（`of` 指向那个父视图），
不是整页 —— 用整页比例去表达卡片内部的偏移，会在父容器本身改变尺寸时漂移。

### 3.3 「对齐」优先于「算位置」

两个元素视觉上在同一水平线时，正确表达是**对齐关系**（`centerY` 相等、`baseline` 相等、
`top` 相等），不是各自算一个比例让它们在探针设备上数值巧合相等。
前者在任何一个元素尺寸变化后依然成立，后者立刻散架。

## 4. 推演一：父容器尺寸变化时

设父容器宽度从 393 → 430（间距与内边距本图省去）：

| 元素 | 声明 | 393 时 | 430 时 | 结论 |
|---|---|---|---|---|
| 主按钮 | `bounded` 高 `>= 44` | 高 44 | **高 44**（内容未增高时） | 下限是常量，上限由内容决定 |
| 图标 | `fixed` 24×24 | 24 | **24** | 视觉常量，不参与求解 |
| 正文 | 字号 `fixed` 17 | 17 | **17** | 字号是视觉常量，不缩放 |
| 全宽 CTA | `pinned` 左右各 16 | 宽 361 | **宽 398** | 尺寸变了，但变的是「被父容器闭合的那部分」，边距仍是 16 |
| 卡片（居中，宽 = 父宽 × 0.82） | `proportional` | 宽 322.3 | **宽 352.6** | 确有此比例关系，才用比例 |
| 内容列 | `bounded` max 640 + 居中 | 宽 361（受父容器限） | **宽 398**（未触顶） | 触顶后不再增长，居中留白 |
| 卡片内标题 | `pinned` 距卡片顶 24，`of: 卡片` | 距卡片顶 24 | **距卡片顶 24** | 基准是直接父视图，父容器变宽不影响纵向关系 |
| 同一标题若误写 `of: root` 比例 | 顶 = 页面高 × 0.155 | 132.1 | **133.3** | 父容器尺寸一变，本该不动的位置漂了 |

**两条结论：**

1. **尺寸由闭合方式决定**：`fixed` 的点值两次求解逐字相同；`pinned` 的尺寸随父容器重算；
   `intrinsic` 随内容重算；`bounded` 在边界内自由、触顶即停。约束求解器解的是**位置与被闭合的量**，
   而不是「所有尺寸都固定」。
2. **位置是约束**：父容器变尺寸时，位置**重新求解**——贴边的跟着动，居中的留在中心，
   比例的按父容器缩放。这正是「不采用等比缩放」的实现含义：**没有全局系数参与其中**。

## 5. 推演二：屏幕分辨率差异

要分三种「分辨率差异」，混为一谈是另一种常见错误：

| 情形 | 例子 | 对 `fixed` 尺寸的影响 | 对位置的影响 |
|---|---|---|---|
| **同纵横比、不同逻辑尺寸** | iPhone 16 同款比例的更大屏 | 视觉常量点值**完全一致**（44 就是 44） | 贴父边/居中的关系自动成立；`bounded`/`intrinsic` 随容器与内容重解；比例关系按父容器缩放 |
| **不同纵横比** | 393×852 → 402×874、iPad、横屏 | 视觉常量点值**完全一致**；`bounded`/`intrinsic` 尺寸按容器与内容重解 | 屏内绝对坐标必然对不上（这正是禁止字面量的原因）；须靠父子约束+安全区重新求解 |
| **同逻辑尺寸、不同物理像素** | @2x / @3x、`devicePixelRatio` 2→3 | 点值一致，物理像素变多 | 布局完全不受影响 |

由此得到三条硬规则：

1. **`devicePixelRatio` 只影响位图资源，不影响布局。** 绝不把 dpr 乘进约束数值；
   @2x/@3x 资源交给资源目录（`Assets.xcassets` / `drawable-*dpi`）解析。
   （`rectInReference == rect * dpr` 是**测量**空间的恒等式，不是实现侧的换算公式。）
2. **安全区与系统 UI 参与位置求解，不参与尺寸。** 刘海/灵动岛/手势条/状态栏只改变可用内容区的
   边界与原点，视觉常量的点值不受影响；`pinned` 关系应贴安全区或内容区而不是物理屏幕边缘。
3. **换屏后「看起来更小」是视觉错觉，不是尺寸被缩放。** 同一物理尺寸的屏幕装下更多点时，
   44pt 的点值不变、物理尺寸不变 —— 若实现里出现了数值差异，说明某处混进了屏幕系数。

## 6. 反例清单（看起来对，其实错）

**A. 缩放类（旧契约的主要敌人）**

| 反例 | 为什么错 |
|---|---|
| 全页系数 `scale = deviceWidth / 393` | 把设计稿宽度当布局规则；两轴比例不同时必然拉伸或留边 |
| 把测量得到的绝对值写成字面量（`leading = 83`） | 有出处、算过，但绑死在探针设备上；换设备即错 |
| 用比例系数表达固定边距（16pt → `0.0397`） | 边距是设计常量，比例化后在别的屏上不再是 16 |
| 用 `transform` / `scaleEffect` 缩放整棵子树 | 连字号、描边、圆角一起缩放，还破坏点击热区 |
| 为了「对上截图」而改整体缩放策略 | 拿整体比例掩盖局部实现错误；位置容差是 2pt，不是「看起来差不多」 |
| 把 `fixed` 视觉常量也比例化（字号、圆角、描边、44pt 触控区） | 破坏排版与可访问性红线 |

**B. 写死类（旧契约的遗留，新契约同样要拦）**

| 反例 | 为什么错 |
|---|---|
| 给 `UILabel` / `UIButton` 写 `widthAnchor = 220` / `heightAnchor = 20` | 文本、按钮的尺寸默认是 `intrinsic`；写死后换语言、开动态字体、窄屏全部截断 |
| 给按钮写 `heightAnchor = 44`（而非 `>= 44`） | 44 是**触控下限**不是固定高度；大字号下按钮被压扁或文字溢出 |
| 把容器/卡片的高度写成设计稿值 | 内容长度可变时溢出；应 `intrinsic` + `minimumHeight` |
| 把设计稿的 `bounds.width` 逐字转成 `constraintEqualToConstant` | 这是旧契约的默认行为，也是新契约要拦的头号问题 |
| 认为「贴边/居中」就够、不需要 `bounded` 上限 | 推到 1024pt 宽时内容会铺满整屏，单列内容被拉成超宽行 |
| 一律 `of: root` | 嵌套组件的内部布局随外层尺寸变化漂移；iPad/横屏上语义完全错 |

## 7. 落地检查清单

写实现计划前：

- [ ] 每个可见元素在闭合方式上归入两轴八类之一（`fixed` / `intrinsic` / `bounded` / `pinned` /
      `proportional` / `equal` / `centered` / `aspect-ratio`），并写出判据；
- [ ] **`fixed` 的每一条都有 `why`**，且理由必须是「固定性本身是设计意图」（图标/装饰/边框/视觉常量），
      不能是「设计稿就写了这个数」；
- [ ] 文本、按钮、容器、内容区域**没有一条**默认成 `fixed`；文本区域若判成 `fixed` 必须显式解释；
- [ ] `bounded` 至少给 `min` 或 `max`；`equal` 给 `with`/`to`；`aspect-ratio` 给正数 `ratio`；
- [ ] 每个元素在位置轴上确定**基准父视图**（写进 `of`），确认不了的一律留待确认，不默认 `root`；
- [ ] `proportional` 只用于确实随父容器成比例变化的关系，且给出理由；
- [ ] 所有 `fixed` 值能在设计稿里直接读到（不是从测量换算得来）；
- [ ] 交互控件用 `>=` 表达触控下限，不用 `==`；
- [ ] **保真底线**：所有闭合方式的选择合起来，在设计稿宽度档上能复现设计稿的排版。

写代码后：

- [ ] 源码中不存在「探针设备推导出来的绝对值」作为布局字面量；
- [ ] 不存在把设计常量乘上屏幕系数的表达式（`* 1.0229`、`/ 393 * screenW` 之类）；
- [ ] 字号、圆角、描边、最小点击区在**同一平台的**全部目标设备上数值一致（跨平台无此约束，双稿各自照稿）；
- [ ] 声明 `intrinsic` 的元素没有定宽/定高的等值约束；声明 `bounded` 的元素出现了
      `>=` / `<=` 原语；声明 `equal` 的出现等值锚点；声明 `aspect-ratio` 的出现比例约束；
- [ ] 可变文本没有固定的字面宽度；多行文本允许高度增高；
- [ ] 必要的 hugging / compression resistance 优先级已设置（谁扩张、谁被压缩是显式的）；
- [ ] 存在冲突约束或 Ambiguous Layout 时为 0；
- [ ] 位置关系全部指向直接父视图（或屏幕画布），无混合基准；
- [ ] 声明了 `adaptiveLayout` 时，**水平**位置比例已收口在 `compact` 档（§3.1.2），
      宽档下的第一层水平位置由 `widthPolicy` 重排；
- [ ] 垂直位置由 safe area、相邻元素、垂直栈或滚动内容链闭合，没有默认套页面高度比例（§3.1.2），
      不被 `firstLevelWidthClass` 收口；较短手机纵向不缺失；
- [ ] 对齐关系用对齐锚点表达，而不是用两个各自算出来的数值凑巧相等；
- [ ] 已实际验证：窄手机 / 普通手机 / iPad 竖屏 / iPad 横屏 / 动态字体（最大档）/ 长本地化文本。

## 8. 规范条款与实现落点对照

| 规范条款 | 落点 |
|---|---|
| §3.1 基准 = 直接父视图 | `dds-schema.json` 的 `parent_id`（主链路，根节点直接父即整屏画布，这是 `of: "root"` 唯一的适用场景）；`bounds` 缺失时用 `page-facts.json` 的 `parentIndex` / `parentHops` / `positioningContextIndex`（`parentIndex == null` 表示直接父即整屏画布） |
| §3.1.2 水平比例只在 `compact` 档、垂直比例始终按高度 | `ui-implementation-plan.json` 的 `adaptiveLayout.firstLevelWidthClass`（缺省 `compact`，**只管水平轴**）+ `scripts/check_adaptive_layout.py`；垂直轴不参与收口 |
| §2 两轴八类 | `layout_proportions.py` 产出的 `relations[].kind`；计划侧由 `check_layout_proportions.py --plan-only` 校验收敛条件（`bounded` 边界、`equal` 对象、`aspect-ratio` 正数、`intrinsic` 理由），源码侧由同一脚本的 `--source` 逐类核对 |
| §2.3 动态字体 | `intrinsic` / `bounded` 的声明 + 源码侧优先级与 `UIFontMetrics` 类缩放通道检查；文本区域判 `fixed` 即列疑点 |
| §3.1 每个区域声明基准 | region 的 `basis` / `parentIndex` / `parent` —— `basis` 与 relation 的 `of` 都指向直接父视图，只是分处 region 级与 relation 级，不是两个基准 |
| §6 反例清单 | `forbiddenLiterals` —— 只收 **`proportional`** 关系的值；`fixed` 的视觉常量（44/24/1/12）与 `pinned` 的内边距（16/24）都**应当**写成字面量 |
| §2 逐类判据 | `check_layout_proportions.py` 按 `kind` 逐类核对，并有 `forbidden-targets-non-proportional` 拦反向错误 |
| §7 交付前清单 | `validate_run.py --source` |

**反向错误与正向错误一样要拦。** 新契约下有两类容易犯的错，脚本必须同时覆盖：

- **漏报**（该松绑没松绑）：设计稿给了一个宽高，实现照抄成固定约束。这是旧契约的默认行为。
- **误报**（该写死当成没做比例）：`icon.width = 24`、CTA 的 `leading = 16`、`borderWidth = 1`
  这类**本来就该照原值写**的视觉常量被当成违规。

判定分两档 —— `> 48pt` 的字面量不可能是手选常量，判 `forbidden-literal-used`；
`≤ 48pt` 与常见设计常量无法区分，只列进 `ambiguousLiterals` 待确认 ——
但这只是**量级**判据，与 `kind` 判据正交：计划说 `pinned`，16pt 就是应当写的内边距；
计划说 `fixed`，24pt 就是应当写的图标尺寸。

> **产物代际**：`schemaVersion < 3` 的 `layout-proportions.json` / `layout-verdict.json` 是旧的一轴
> 口径（非文字元素一律 `proportional`、位置一律 `of: "root"`、`kind` 只有两档），不能当作本契约的样例。
